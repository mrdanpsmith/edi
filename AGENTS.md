# AGENTS.md

Edi is a markdown editor. Frontend: ProseMirror (the document editor) + CodeMirror 6 (embedded code blocks only) + Mermaid + spreadsheet formulas (TypeScript/Vite) compiled to a static `dist/`. Backend: Python 3 + PySide6/QtWebEngine. A native `QWebEngineView` hosts `dist/index.html`; the page talks to Python via `QWebChannel` (`backend/bridge.py`). This is NOT a plain web app — `npm run dev` runs only the Vite server; the real app is Python.

## Inline marks

`src/markExit.ts` owns one rule: **a mark ends at its closing delimiter or when you walk out of it with an arrow key, and both are about the *next* character, never about the text already written.** `**bold** and more` is a sentence with two bold words in it, not a bold block, so neither path touches the document — `stopMarking` (wrapped onto every inline input rule in `src/editor.ts`) writes `storedMarks`, and `markExitPlugin` does the same for `ArrowRight`/`ArrowLeft`. This is the one-off that used to be the code-span rule alone, generalized; `tests` for all of it are `src/markExit.test.ts`.

The whole mechanism is `storedMarks`, so three of its properties are load-bearing. It wins over the document for exactly as long as it stays set, which is why one write is what a closing delimiter means; it is cleared by any step; and `Transaction.setSelection` clears it too, so anything that moves the selection *and* wants to keep a mark has to `setSelection` first and `setStoredMarks` second (the reverse order loses it, silently). "What the next character inherits" is `state.storedMarks ?? $from.marks()` — and note `$from.marks()` at the *end* of a run reports that run's marks, because the position is still its boundary, which is exactly why a finished span dragged the rest of the sentence into itself.

**The arrow only fires where the browser cannot do it itself**, and that is the whole design: the caret has to be at the end (or start) of its textblock's text *and* have no node beyond it at any nesting level (`noNodeBeyond` — no following paragraph, no next list item). Everywhere else the browser's own arrow already moves the caret, and the position it lands on is outside the run, so those presses work and must keep working: handling them would make `→` a key that sometimes does not move the caret. Two traps in that check — `ResolvedPos.index(depth)` is the index *into* that level, so the node at `depth` is `index(depth - 1)`, and the siblings are `node(depth - 1).childCount` (a textblock's own `childCount` is 0, since its text is inline). Only the **innermost** mark is left (a mark set is rank-ordered and `code` is innermost, per `orderedMarks`), so `→` out of a code span inside bold leaves the bold.

**Every delimiter's opening run has to be a whole run on *both* sides of it** — a lookbehind so the pattern cannot start inside a longer run, and a lookahead so it cannot start one — or a shorter sibling pattern steals the pair mid-typing: typing `~~strike~~` reaches `~~strike~` first, and the subscript rule's `~…~$` matches `~strike~` inside it (its inner group is `(.*?)`, so it may swallow a `~` of its own), which made strikethrough a subscript. `createPairedDelimiterMark` carries both guards for `==`/`~`/`^`; `inlineMarkRules` carries the lookbehind for `**`/`*`/`` ` ``/`~~`, whose inner groups already exclude their own character.

`Ctrl+Alt+C` is the only keyboard shortcut for inline code (`formattingKeymap` also has Mod-b/Mod-i). `Mod-Shift-C` is **copy file path** in `src/main.ts`, so do not reach for it, and `Ctrl+Shift+C` is a browser/devtools combo; `Ctrl+E` is fine but was not what the user wanted.

## Find / replace

`src/search.ts` is a ProseMirror plugin + pure matching layer; `src/searchPanel.ts` is the `#edi-search-bar` UI. Search runs over the document's raw flat text — every text node (including fenced code blocks) plus the `attrs.value` markup of `table`/`mermaid_block` atoms — and highlights matches on the rendered editor via inline decorations (with whole-block `NodeSelection` for atom matches). Masked fields, images and source blocks contribute no searchable text. Replace preserves marks; a table's pipe value refuses a replacement containing `\n` (row corruption). The document focus follows the search: typing or toggling a flag jumps the caret/scroll to the first match while the panel keeps keyboard focus (plain doc edits do NOT reset the active match — `SearchPanel.refresh()` re-applies only after a doc swap), Enter/Shift+Enter step matches, and spreadsheet/plain view tables additionally scroll the cell under the match into view (`onSearchChange`/`scrollActiveCellIntoView` in `src/node/table.ts`). Esc closes, Ctrl+F opens find and Ctrl+H the find+replace bar (wired in `src/main.ts`, `src/menus.ts`, `backend/window.py`'s Edit menu).


## Spreadsheet formulas

`src/formulas.ts` is the single source of truth for the function registry and value/coercion helpers; `src/spreadsheet.ts` is the parser/evaluator and evaluates through a `FormulaEnv` (`{ functions: ReadonlyMap<string, FormulaFunction> }`, looked up case-insensitively). `solve`, `computeSpreadsheet`, `resolveTableValue`, `proseToMarkdown`, and `serializeDocToHtml` all take an optional env that defaults to `BUILTIN_ENV`, so any path that re-serializes a resolved table must thread the document's env through (the editor's `getMarkdown`, export, and the table node view all do). `series.ts` derives `FORMULA_FUNCTIONS` from `BUILTIN_FUNCTION_NAMES`, and `formulaReference.ts` generates the Help → Formula Reference document from `BUILTIN_FORMULAS`, so a new builtin cannot drift between the evaluator, reference-shifting, and docs.

Document-local functions come from `code_block` nodes with `language === 'edi-formula'`, one `NAME(params) = expression` per line (`#` starts a comment). `src/formulaDsl.ts` parses/compiles them, rejecting builtin-name collisions, duplicate names, and cycles; `src/formulaDefs.ts` is an editor plugin that compiles every such block (document-wide) into a `FormulaEnv` in plugin state, decorates rejected blocks with `.edi-formula-invalid`, and exposes it via `formulaEnvFor(state)` / `documentFunctionsFor(state)`. Builtins are never overridable, and a rejected definition makes cells that call it resolve the usual `#NAME?` error. Function-name autocomplete lives in `src/formulaAutocomplete.ts`, fed by the table node view's `formulaFunctions()` (builtins + document defs).

## Mermaid visual editing

`src/mermaid-edit.ts` is the whole visual-editing layer: `renderDiagram()` (a thin wrapper over mermaid + `responsifySvg`/`adaptDiagramColors`/`pinSvgTextColors`/`attachMermaidToolbar`/`bakeDiagram` from `src/mermaid.ts`, so the node view no longer owns that pipeline), the source patchers, the inline label editor, the kanban drag, and the notice that keeps the last good diagram on screen when the patched source stops parsing. `src/node/mermaid.ts` keeps the node view plus the mode plumbing: the `mermaid_block` `_edit` attr, `MERMAID_EDIT_KEY` (at most one diagram in edit mode, like tables), `enterDiagramEditMode()` / `exitDiagramEditMode()` / `toggleDiagramEditMode()` (wired to the hover toolbar's Edit/Done button, a double click, and the Edit diagram / Done editing context-menu items in `src/main.ts`).

Two rules the rest of the app depends on:

- **The fenced source is the document.** A visual edit is one `setNodeMarkup` transaction (`commitSource`), so undo takes a whole edit back. `commitSource` must NOT pre-set `this.currentCode`: `update()` uses it to spot a changed value, and pre-setting it makes the view skip the re-render, leaving the old diagram on screen (there is a real-engine test pinning this).
- **View mode may bake, edit mode must not.** A diagram with light native text (sequence diagrams) is baked to a bitmap in view mode, which removes every clickable label; entering edit mode re-renders the vector and marks the labels with `.mermaid-editables`.
- **Leaving edit mode must resolve the layer.** The label input is a child of the `.mermaid` block, not of the container a render replaces, so a re-render alone leaves it floating over a diagram that is no longer editable — still swallowing its own events, and holding a source snapshot that has since moved on. `exitDiagramEditMode()` (and the diagram `enterDiagramEditMode()` drops) therefore calls `finishMermaidLabelEditing(nodeDOM, true)`, which *commits* a label edit in progress, exactly as a click elsewhere would: Done's own `mousedown` calls `preventDefault()`, so the input never blurs and nothing else will resolve it. The mode transaction is dispatched **first** on purpose — the re-render it triggers then already sees `_edit: false`, so the commit's render cannot race an edit-mode render that would re-mark the labels. A plain re-render calls the same resolver with `accept: false`: nobody asked for it, and its source may have changed underneath the editor.
- **A double click anywhere ends edit mode.** The plugin's `dblclick` handler toggles the diagram under the pointer, and otherwise finishes whichever diagram is in edit mode — the gesture that turns the mode off should not have to land back on the diagram. The click is never swallowed (word selection still happens); only ones Chrome owns are left alone: `a[href]`, `button`, `input`, `textarea`, `select`, `.cm-editor`. The listener is on the editor's **scroll container** (`view.dom.parentElement`, i.e. `#editor-container`), never on `view.dom`: the editor's own box is only as tall as its content, so a document that is one short diagram (a lone board) leaves the white space under it on the scroller, where a `view.dom` listener sees nothing — the mode stayed on and Chrome answered the click itself by selecting the nearest text on the page, the document name in the status bar. It is the scroller and not `document` (which `src/node/table.ts`'s handler can afford) so a double click in a dialog sitting on top of the editor cannot reach through it. `tests/test_window.py::test_double_click_below_a_lone_board_ends_its_edit_session` pins it with the real gesture at real coordinates, asserting the point is outside `.ProseMirror` first.

**Only mappable labels are offered.** `labelTargets()` marks a label `.mermaid-editables` only when `resolveLabelSpans()` maps it to a source range *right now* — that single filter is what keeps the promise the UI makes (a label you cannot click is either Mermaid-computed, like a treemap total, an xy-chart tick, a packet bit range, a kanban assignee, a Wardley stage or a `<<stereotype>>`, or it repeats in the source with no way to tell the copies apart). Adding a family means adding a mapper, not touching the DOM walk. A `LabelRole` of `entity` marks a label the diagram refers to elsewhere (ER entity, state, class, git branch, requirement, sankey node, wardley node, venn set, journey actor), so its rename rewrites every reference via `all: true`; `text` is prose that sits in the source once. `sourceLines`/`wholeWordSpans` are the shared source-scanning primitives — match whole words, not substrings, or `date` matches inside `order_date` and the label goes ambiguous. A label mermaid wrapped across `tspan`s reads back from `textContent` with its spaces dropped (`Lack ofTraining`), so a whitespace-squeezed match records the source's own spelling in `sourceText` and the editor edits that, not the rendering's. The same holds wherever mermaid drew the source's text inside something else — a sankey node shares its element with its computed total, a requirement row is drawn under mermaid's own idea of the key (`verifymethod: test` shows as `Verification: Test`) — so `sourceText` is the source's spelling of whatever the mapper's span covers, and the input holds exactly what a commit replaces. That is also why the editor resolves from `target.text` and not from the edited text: a row is *found* by the row mermaid drew and only its value is rewritten, so a typed value alone would leave the mapper nothing to find.

**Two gates, two costs.** `tests/test_window.py::test_every_offered_label_rename_resolves` is the cheap gate: one rename per diagram, one case per distinct patch strategy (text, tspan-wrapped, entity-all-refs, value-only row, sankey first line, implicit git branch, withheld total), ~3 s for the whole set, inside the session window. It asserts the one thing that is never acceptable — the editor closed and the source never changed — and that either mermaid drew the value or the notice said it would not. `scripts/mermaid-label-probe.py` is the exhaustive one: it walks *every* offered label of *every* template through the real gesture path, prints the offered/withheld split, and exits non-zero on any silent no-op or render failure (`--type` to narrow, `--first` for a smoke pass, report into `build/`). It needs its own WebEngine page, so it stays out of pytest — that is what the two-window constraint above is about. Run it after touching mappers, mappers' regexes, or the `GENERATED_BY_FAMILY` lists; it is the only thing that can see mermaid's real DOM shape (it found the `diagramFamily` case bug and the ER substring bug, which no jsdom test could).

Mermaid's own SVG is the DOM to patch, so read it defensively: a label may be a `text` with a `tspan` child (sequence participants are `text.actor > tspan`), which is why the wrapper check upper-cases `child.tagName`. Chromium also makes `.items > .node` natively draggable, and its drag swallows the pointer stream the kanban drag listens on — cancel `dragstart` (`-webkit-user-drag: none` in CSS covers the rest). Do NOT `preventDefault()` on `pointerdown` to fix that: it would suppress label-editor clicks.

**A kanban drag moves the real card — or the whole column — and the indicator has to be *under* it.** `armDragGroup` (in `src/mermaid-edit.ts`, via `armCardDrag` / `armColumnDrag`) lifts the elements the press landed on: the transform is *appended* to the one mermaid gave each (`base + translate(dx, dy) scale(1.04)`), so restoring the drag is putting strings back rather than recomputating positions, and `stop()` always does it. A card drag lifts the one `g.node`; a **column** drag lifts the band's `g` from `.sections` *and* every card whose centre falls in that band, so the column moves with the cards still in it and one undo takes the whole move back. A card is detected by `cardAt(pointer, cards)` (direct `closest('.items > .node')` target, falling back to a coordinate hit-test through the shared `drawnElementAt`) and only a press that hit *no* card can arm a column, so a card is never mistaken for the column it stands in; the column's own frame excludes its header label so the `⋯` and the column name stay clickable. The offset is divided by the mapping `svgMapping(svg)` reports — viewBox origin, rendered rect and a scale per axis — because a drag is measured in screen pixels while the card is moved in a viewBox mermaid has scaled to fit; without it the card runs off twice as far on any board that is not drawn at 1:1, and reading one scale for both axes would drift on a container that letterboxes the drawing. Three things have to hold together here, and each was a bug before it was a rule: the svg clips (`overflow: hidden`) and `.mermaid-preview` scrolls, so the preview gets `.kanban-dragging` to switch both to `visible` or a card travelling off the board is cut off under the pointer; SVG paints in document order, so the card is re-appended to the end of `.items` (all cards are one sibling list) to be on top, and `stop()` puts it back before its own place — the model→element mapping is the *captured* `cards` array, which re-appending does not disturb, but a fresh `cardElements()` walk would; and the drop line is an svg `<line>` *inserted before `.items`*, so it is over the column's own opaque background but under every card, the dragged one included (and before `.sections` for a column's, so it is under the frames it stands between). It cannot be a positioned overlay: a child of the preview paints above the whole drawing (`z-index: 4` did exactly that, and the line drew across the card it was previewing), and the `.mermaid` host puts it *under* the board instead. Being svg-native also means `vector-effect: non-scaling-stroke` holds it at 3px on a zoomed board and its endpoints are written in the drawing's own user units, so no scroll or zoom correction is needed; a line outside the board would have to be positioned from `container.getBoundingClientRect() + container.scrollLeft`, like the `⋯`. The line itself (`dropLineAt`) is drawn in the gap the release acts on, spanning the column and overhanging it by `DROP_LINE_OVERHANG` (mermaid's cards are ~15px narrower than their column, so an inset line is completely hidden by the card that is about to fill the gap); the vertical offset is `DROP_LINE_GAP`. **A drawn slot ends the column; it is not a card in it.** `dropColumn` is where that is decided — the slot's rect comes back as the column's *end* rather than as one more sibling — and both the index and the line are computed from what it returns, so a pointer over the foot of a column is the pointer over the last real gap. Counting the slot instead put the line in a gap *below* the last card that no release acts on: the card lands above the slot (the authoring source is rebuilt with the slot appended last, whatever the patch did with it), so the line was promising a place that does not exist. It matters because the foot of a column *looks* like the slot — that is where the `+ Add a card` is drawn — so this is the gesture every drag to the bottom of a column makes. It was a bug before it was a rule, and it survived the last round of gates because `_pointer_drag(aim="last")` aims just below the middle of the last *real* card, which is still above the slot: `tests/test_window.py::test_kanban_drop_line_stays_above_the_drawn_slot` aims at the slot's lower half, past the point where a slot-as-a-card would have counted. A **column** drag is the same machinery with the slot question answered differently: `dropSections` is what tells the two apart, the counterpart of `dropColumn` on the card side — the real columns go into `rest` with the dragged one lifted out, and the drawn `+ Add a column` comes back as the board's *end* rather than as one more column in it. `columnSlotAt` counts which gap line the pointer is over (gaps strictly before the pointer, counted against `rest`, so a pointer over the dragged column's own band does not shift the count) and `columnGapAt` is that gap taken from the two columns on either side of it, full height. **The drawn column ends the board; it is not a column in it**, so the last gap is the one *before* it — a pointer over its right half is the pointer over the last real gap, and a column dropped at the end of the board lands there, leaving the slot the last thing drawn. Counting it instead drew the rule at the slot's own right edge, out past the board, offering a place after it that no release acts on: the mirror of the card bug above, and the board's last column *looks* like the slot, so it is the gesture every drag to the right of the board makes. It was a bug before it was a rule, and it survived the same way the card one did — `_pointer_drag_column(slot=1)` aims past the last *real* column's right edge by 24px, which lands 24px into the 200px drawn column, comfortably before its middle and so also the gap in front of it. `tests/test_window.py::test_kanban_column_line_stays_left_of_the_drawn_column_slot` aims at 75% of the drawn column's width instead, past the point where a slot-as-a-column would have counted. A column boundary is a single unambiguous line, so unlike a card it needs no `DROP_LINE_GAP`/`DROP_LINE_OVERHANG` nudging — `createDropLine` takes them as 0. It is the only part of a drag that answers "which slot", since a card over a three-card column can go to the first, second or third and the column outline cannot say. It is placed on *every* move, not only when the column changes, and it hides itself off the board (a release there does nothing). A column with neither cards nor a slot has no gap, so its line is centred in the band — and a drawn slot makes even an empty column card-tall, where the last gap is above the slot like any other. The card is never dimmed: it is lifted, not ghosted, and the hole it leaves is the record of where it came from. **A card is scaled, a column is not**, which is why `liftElements` takes the scale as an argument and `armColumnDrag` passes `1`: a card is one `g`, and `scale(DRAG_LIFT_SCALE)` about its own local origin says "this is in the air", but a column is a *frame with a padding and cards inside it* and an svg transform scales about the *element's* origin — so a scaled frame grows its border and padding and pushes its cards out through the bottom, and the ones near the edge fall out of the section entirely, which reads as a column of the wrong shape travelling somewhere other than where it was dropped. A `scale` on a column's transform is a bug. **A column is not held where a card is, because it is not one element.** The board is two sibling lists — the frames in `.sections`, the cards in `.items`, the frames *first* — so every card on the board is painted over every frame, and a lift that re-appends each element to *its own parent* (right for a card, one `g` in one list) can lift a frame over the other frames and nothing else: a column in flight was drawn with its neighbours' cards lying across it, and a column *passing over* a neighbour's cards looked like it had picked them up — which is how an empty `Done` at the end of a board came to look like it was carrying `Specified`'s card. So a column's lift is a group of its own (`kanbanDragLayer`: an svg `<g class="kanban-drag-layer">` appended as the **last** child of the svg, frame first and then the cards it carries, which is the order the board itself is drawn in) and `liftElements` takes it as its `into`, putting the whole set in the one parent — its per-element restore is unchanged, because every element's own place was captured before it moved. Nothing about how either element is *painted* changes: mermaid's kanban styles key on the element's own classes (`.section-N rect`, `.node rect`, `.kanban-label`), never on the list it is in, which is worth knowing before moving anything else between those two lists. The line stays *under* the held column, the way a card's does, and `stop()` removes the group whether the drag started or not. The restore runs **backwards** for the same reason: each element goes back before the `follower` it was captured with, and with the set in a group that follower is often another lifted element still standing in the group — restoring in capture order throws `NotFoundError` on the first card, which aborts the rest of the restore *and* `hooks.drop`, so the drop is silently lost and the rest of the column stays in the group. A held card is also `pointer-events: none` (so the drop is read off the pointer, not off whatever it passes over), which makes the group invisible to a hit test — `elementFromPoint` therefore cannot answer "what is painted over the held column" without the helper lifting that for the sample (`fronted`), which is why that probe restores it rather than leaving it. The cursor says the same thing without a drag: an open hand over a card or a column, a closed one while it is in the air (`DRAG_CONTAINER_CLASS` goes on the *preview*, so the dragging rule is `.mermaid-preview.kanban-dragging …`), and a text caret over a slot — the grab rules exclude the two slot classes rather than out-specifying the caret, because a slot is nowhere and so is not held by anything. The `⋯` and the `✕` *are* positioned siblings of the svg, so they do paint over the line where the two meet — the real-engine probe therefore samples the line along its run (`overLine`) rather than trusting one point, and `elementFromPoint` is the check throughout, since a screenshot of a just-mutated DOM under the offscreen platform is a stale frame and will lie.

**A board is authored from the board, and its chrome is quiet until the pointer asks.** `attachKanbanChrome` (in `src/mermaid-edit.ts`) builds the whole layer in one pass: per real column a `mermaid-kanban-menu` `⋯` (`<column> column actions`). All of them share `KANBAN_BUTTON_CLASS` (`mermaid-kanban-btn`), and the open menu list and every composer are inside `KANBAN_CHROME_CLASS` — the classes `src/node/mermaid.ts` `stopEvent` and the `dblclick` handler recognise as chrome, so a press or a double click on any of them is the control's own and never reaches the diagram under it. **There is no per-card control at all**: a card is deleted by dropping it on the drawn column slot (above), so the layer has one mark per column and nothing over a card. **Adding is not in this list at all**: the board is *drawn* with somewhere to add, so the places to add are part of the diagram (below) rather than controls laid over it, and `attachKanbanChrome` has nothing to say about them — which is also why the layer's `place()` is the only thing that can move a control and never a slot.

**A column's `⋯` is on the same line as the column's name.** `menuBox()` measures the name's own box (`headerTarget(band)`, the same target a click on the header renames) and centres the mark in it, because the name is what the eye puts the mark against and the band's own top edge is not where the name is — the band is padded and the name is drawn inside that padding, so the old `band.top + KANBAN_BUTTON_EDGE` put the `⋯` several pixels *below* the text it is the menu of. That is not a claim a hit test can make: nothing overlapped anything, the control was in the right column and clear of the name (`_menu_in_its_band` passed all of it), and the only way to see it was to look. A band is the fallback for a name with no box of its own — one that is not offered (a repeated name has no single target) or one not laid out yet, which measures as no height. **One control is always on screen.** The `⋯` belongs to the whole board, so it is quiet (a flat mark) but permanent: a board that hid its only way to delete a column behind a hover would be a board you could not get out of. `columnAt` refuses a press on a column's own name, because that is a rename. Nothing is concealed any more — a card is not a control surface — so the layer has no reveal to make and no `is-shown` to read.

**The menu is a popover over a board, not a dialog on it.** One at a time (`closeMenu`), and the `⋯` that owns it is remembered (`openMenuFor`) so pressing *that* one is the toggle and pressing any other is a move — without that, a second `⋯` could only ever close the first menu. The list hangs off its own `⋯`: right-aligned to it and `MENU_GAP` under it, pushed through `place()` immediately rather than on the next resize, because the list is built long after the layer's own `place()` ran and would otherwise sit over the first column. A real column that is not the last one gets exactly `Rename column` / `Delete column` (the last one gets no delete, and the drawn column at the end gets no `⋯` at all — it is not a column yet), and the rename is wired to *the very mapper a click on the header uses*, found by position (`targets.find((entry) => section.contains(entry.el))`) rather than by name — two columns may share a name. **No item names the column.** An item belongs to the `⋯` it hangs off and that `⋯` already says which column it is, so a name in the item is a name repeated in a place a *translation* of it would have to be kept in step with the prompt's; the prompt (`promptForKanbanDelete`) is the one place that names what goes, and it still does. The corollary is that the menu is `MENU_WIDTH` wide and the *text* is bounded by it (`white-space: normal`, `overflow-wrap: anywhere`): a label wider than the menu wraps inside the popover instead of widening it off the board, which is what stops a column with a 60-character name pushing a control past the edge of its own column. Escape and a pointer off the menu or the board take it away, and **the menu is its list *and* the `⋯` it hangs off** — `isOnMenu(target)` whitelists both, using the `openMenuFor` that already answers "which `⋯` is this". Hovering the owning mark is not leaving the menu: the walk from an item back up to the button that opened it is the other half of the same gesture, and it closed the list every single time, which reads as the menu being unable to survive a second look. A *different* column's `⋯` is a move rather than a return, so it does still take it away — only the one that owns it is the menu's own. A press anywhere that is not the list does take it away too, and the `⋯` and the items stop the press reaching it, so the `⋯`'s own click is the toggle. **There is no gap between the `⋯` and its list, because a gap is a hole in the popover.** The list is placed at the button's own bottom edge (`menuBox()`'s height, not that plus anything), right-aligned to it, so the menu hangs off the `⋯` that owns it and the two touch. It used to be placed 6px lower, and the gap was a strip of *board* between a button and the menu it had just opened — which is what a floating menu looks like. The pointer crosses that strip on its way down to the items every single time, so it was bridged: the list drew a `::before` over the gap of exactly its height, and the one number both halves read (`--mermaid-kanban-menu-gap`, with `menuGap()`'s 6px fallback) is why a stylesheet and a placement could not drift apart. **A bridge with no background closes a hole for a hit test and not for the eye**, so that is all it did: `elementFromPoint` over it reported the list, every real-engine gate passed, and what the user saw was the board — a bug the whole walkability story was built to prevent, and one this project's own rule about not trusting a *visual* claim already covers. The gap, the variable, the read-back and the pseudo-element are all gone, since with the boxes touching there is no hole to bridge. What still stands is the part that is not about geometry: `menuList` stops `mousedown`, so a `click` can never be born out of a press the board ate, and the walk down from the button is answered by the two boxes themselves — `tests/test_window.py::test_kanban_menu_and_drawn_add_and_delete_columns` samples every pixel from inside the `⋯` down into the list's first row and asserts the whole run of answers is `['its button', 'the menu']`, with `elementFromPoint`, so anything else painted between them (a gap, a stray sibling) fails it.

**The board is drawn with somewhere to add, and the document never sees it.** A board's shape is obvious while you are looking at it and not at all once it is a paragraph of source, so the places to add are *drawn*: `kanbanAuthoringSource` (`src/mermaid-edit.ts`) appends a `slotc<n>` card to every column and a `slotn` column to the end — **and a card slot inside that column too**, so the board is drawn ending in a column with somewhere to put the card you are about to add rather than in a bare header, and so a card has a column it can be deleted into — which is the bin, and is painted **only** while a card is in the air (the deletion paragraph below), each carrying `KANBAN_CARD_SLOT` / `KANBAN_COLUMN_SLOT` as its label, and the node view renders **that** while the diagram is editable (`src/node/mermaid.ts`), never the document's own source. A drawn slot is therefore laid out by mermaid itself, which is the whole of why it beat the controls it replaced: an empty column's band is sized to its header alone, and a 24px bar laid over that name covered the rename target — where a card-shaped thing drawn *in* the band makes the band a card tall, gives every column a place to add without a single absolutely-positioned sibling, and cannot collide with the toolbar or a horizontal scroller, because it is not one. The reserved ids are what make this safe: `/^slot[cn]\d*$/` is an id nothing else on a board would carry, so a card the user has genuinely titled `+ Add a card` is a real card (`isKanbanCardSlot` / `isKanbanColumnSlot` are the only readers), and every commit runs the source back through `kanbanRealSource`, which strips an untouched slot and keeps a *named* one as clean content (`[Fresh]`, `col1[Archive]` — a fresh id from `freshKanbanId`, which steps over the ids already on the board, cards included) — the document is never asked to hold a slot. Everything that used to walk the board as chrome has to know the difference: `kanbanColumnCount`/`realKanbanColumns` answer "how many columns" (the menu offers no delete when it is one), `cardsIn`/`kanbanColumnCardCount` answer "how many cards" (a delete prompt must not claim it is taking slot cards), and `slotAt` is where a *new* card goes — the drawn slot's own place, so the slot stays the place the next card would go. A press on a drawn slot is a request for a title, not a drag: the pointer handler returns before `armCardDrag`/`armColumnDrag`, and the drawn column is not a column to drag either. `onSlotClick` finds the slot with `drawnElementAt` (the event's own target first, then the coordinate hit test) and then *defers to the label editor*: a click on a label is that label's business, so the column slot hands `headerTarget(band)` to `openLabelEditor` and a new column is named by the very editor its own header is renamed by. A card slot instead opens the composer at the slot's own `box()` (`slotComposerBox`) — **except the card slot in the drawn column**, which is the bin when a card is in the air and is *still* a column to name at rest, so a press there is routed on by the column's own band rather than answering a question about a card that was never offered, which is why an in-place assertion reads the field and the slot in *one* snapshot — the page settles between two reads, so two boxes read at two moments are two moments of the layout, not two boxes. **A drawn slot's label is a placeholder, so the field that writes over it is empty.** A card slot is not even a label target at all (the card filter in `attachMermaidEditing` drops it, and its composer opens from the slot), but a column's *is* one — its name is a label like any other, which is the whole reason the slot can be named by the editor that renames it — so the *same* press on a slot's text and on the band around it must not open two different fields. Both therefore pass one `FreshField` (`columnField(band)`: empty value, `placeholder: 'Column name'`, `tone: 'new'`, the band's width at `COMPOSER_HEIGHT`) into `openLabelEditor`, and the generic click handler works it out from the *same* slot walk (`slotBand` is `sectionElements(svg)[slots.column]`, not a CSS class, so a class that outlived its render cannot make a real header open empty). What is being filled is a column, so the field stands in the band and not over the text on it, and `RENAME_FIELD_WIDTH`'s floor is dropped: a band is already wider than a name. An empty commit is refused by the `usableKanbanLabel` guard every label already had, with the same reason a card gives — a `kanban` header with nothing in it is not a column.

The layer is positioned the way the drag indicator is *not*: these are absolutely-positioned HTML siblings of the svg, from `container`-relative rects through one `place()`, and what `place` reads is *re-read on every event that can have moved it*: a `ResizeObserver` on the svg, on the preview **and** on the editor scroller, plus their `scroll` events. The svg alone is not enough (a window resize narrows the preview while the svg keeps the size mermaid drew it at, so the observer never fires), the preview alone is not enough (a composer hanging below a short board scrolls the *editor*), and no observer covers the rest: the board is *centred* in the preview, so the svg slides inside it when the block around it grows, moving every control without changing the size of anything measured. So an event asks `schedule()` rather than placing directly, and a `place()` that moved something asks for another — a self-limiting settle loop that ends as soon as a place moves nothing, which is what makes a re-placement a convergence rather than a per-frame cost. Every re-render *rebuilds* the layer, so the controls exist only in edit mode and are gone after Done. It is offered only where the walk is trustworthy: `cardElements(svg)` must match the parsed model's card count, and the columns must match the sections', or the layer is skipped rather than offering to delete something it cannot name. The drawn slots are none of this — they are drawn by mermaid, laid out by mermaid, and repositioned by mermaid.

**A card is deleted by dropping it on the column the board is drawn with, because a card's corner is its own title.** Mermaid lays a card's label into the *whole* inner width, so a title long enough to fill its card runs right up to the card's edge (measured: a 185px card, a label box 364.5→539.5 against a card 354.5–539.5) — the top-right corner is drawn over the first line of exactly the cards a user most wants to read, and there is no padding to move a ✕ into and no second corner that is not the same problem. Moving a mark *out* of the card is worse still: the band's corners are rounded, so a mark hanging past one is over the page rather than over the card. So the ✕ went, and the board answers instead: for the length of a card's drag, the drawn column slot at the end of the board — a place to add a column, and the one thing on the board a card has no business in — **is** the bin, and it says so. That column is drawn *with a card slot in it* (`kanbanAuthoringSource` appends `slotc${doc.columns.length}` under `slotn`), and that card slot is the bin. **At rest it paints nothing** — a card captioned `+ Add a card` standing in a column captioned `+ Add a column` is the one place on the board offering a card to a place, and the press it invites is answered with a *column*, so the caption is a caption over the wrong answer. The space is still drawn (mermaid sized the band around it, and **a drag may not re-render the drawing**, so the space cannot be added on demand) and is emptied by class instead: `attachKanbanChrome` puts `mermaid-kanban-bin-slot` on that one slot on every render, the stylesheet takes its frame and its label off with `display: none`, and `kanbanTrash`'s `show()` takes the class off in the same turn that writes the bin's words on it (`hide()` puts it back). `display: none` rather than `visibility: hidden` is what makes a press in the empty space a press on the band — the one that names the column. `kanbanTrash` (in `src/mermaid-edit.ts`, armed by `DragHooks.begin`/`end` so it appears when a *press becomes a drag* and not on the press, since a press on a card is a rename) does not lay a control over it: it mutates the drawing, dressing *two* parts of it — the band and the card slot in it — with `--danger` on their own `<rect>`s and `trashIcon()` in their own names, and `hide()` puts both back from what it saved. **Both halves say it, because the card in the air covers the one you would rather read**: the held card is 192px wide and the bin card slot is 185px, so the pointer is over the slot and the slot is under the card, and the band above it is the half that stays on screen. Dressing only the card is the whole bug that shape caused — a bin that is only ever legible when nothing is on top of it. **The bin is of the drawing, not laid over it**, and that is not a style preference — it is what makes it legible: a card is a `g` in `.items`, a column is a `g` in `.sections`, and `.sections` comes *first*, so every card on the board is already painted over every frame, and a lift re-appends the held card to the end of its own list. An HTML panel is a child of the preview and paints over the whole drawing, the very card on its way to the bin included — so the one thing you could read while deciding was hidden behind the thing to drop it on. It cannot be re-rendered into either: a re-render mid-drag takes the held card with it, which is the same reason the drag never re-renders. The bin **replaces** the words on both halves rather than adding a caption over them, so the column reads as one thing for as long as the drag lasts, and it is gone before any *press* could reach it — which is what keeps the two gestures on one column from colliding (a press anywhere in that column, *including its card slot*, still names a new column: `onSlotClick` routes a press in a real column's card slot to the card composer and anything past the drawn column's card slot through to the column's own editor, and that is the other test's claim). While the pointer is on it both halves are lit (fill-opacity `0.14`→`0.28`, stroke `2px`→`2.5px`, and deliberately **not** the `kanban-drop-target` class a drop target is marked with — a second border round a bin) and the drop line stays hidden, so the two answers are complementary: nothing is promised where a card cannot land, and a lit bin is what is offered instead. The delete is still the same `promptForKanbanDelete` the ✕ used, and `armColumnDrag` is untouched: a *column's* end is a gap, not a bin, and `dropSections` already reads it that way. The label is read the way mermaid drew it (`.cluster-label .nodeLabel`, with a `.cluster-label p` fallback for a renderer that uses one). **The two halves say different amounts of the same sentence, and that is measured, not chosen**: mermaid sized each label box to the words it drew — the band's for `+ Add a column`, the card's for `+ Add a card` — and a `foreignObject` clips in *both* axes, so a bin that said one fixed string in the card's box was showing `Delete` and cutting `card` off. Both strings are fixed, so both boxes are the same size on every board: the band says `Delete card` (116px in a 128px box) and the card says `Delete` (76px in a 105px box). The mark is drawn as an **inline** svg for the same reason and needs a `display` of its own to stay one: the drawing's own `.ProseMirror .mermaid svg { display: block }` rule made it a block, and a block mark pushes the words after it onto a second line that the one-line box then cuts. Its colour is **inline on each path** for a third reason, and it is the one that was invisible in every measurement until the paths themselves were read: mermaid styles `path` inside a board with its own palette, and such a rule beats both an inherited value and a presentation attribute, so the mark came out stroked *and filled* in the diagram's colours while the words beside it were the danger colour — an element reading `--danger` and a mark that is not. Nothing short of an inline style wins that, and `var(--danger, currentColor)` is the fallback so it can never end up with no colour. All three were found by measuring in the real engine rather than by looking: `KANBAN_TRASH`'s `fits` asserts both axes and its `markStroke`/`markFill` are read off a **path**, not off the mark, and a screenshot of a just-mutated DOM is a stale frame that would have been believed instead. `tests/test_window.py::test_a_card_dropped_on_the_board_s_slot_column_is_deleted` walks the whole gesture in the real engine and pins the paint order *structurally* — the frames before the cards, the held card last in its own list, the card's box over the pointer, the band's box under it — because a held card is `pointer-events: none` (see the drag paragraph) and a hit test therefore cannot see it at all; it also asserts both label boxes hold their own words whole. Five jsdom cases cover the tint's own values on both halves, the different words on the two, the Cancel path and the two ways it must *not* appear.

**A composer is taller than the slot it fills, so the block grows for it.** A field is absolutely positioned, so it contributes nothing to the block's height — and an empty column's band is only a header and a card tall, so a field asking for a long card title hangs below the band, and at the end of a document the part that hangs is not something the editor can scroll to: the dialog is simply cut off. So `openInlineInput` measures the difference and sets the block's `padding-bottom` to it (`FIELD_MARGIN`), scrolls the field into view only when it really grew, and puts the padding back on close. It also takes the rect as a *function* when the caller has one (`spec.rect: DOMRect | (() => DOMRect)`, reported through `onPlaced`) and is repositioned from the chrome's `place()` like every other control, because a composer stands where the control it replaced stood and the board moves under it; the chrome drops the entry as soon as the field is gone, which is the only signal that it closed. A column's name is one line and it is edited by the label editor, not by a composer, so `COMPOSER_HEIGHT` only ever sizes the *card* composer — which is the one that grows with the title, and the one that can be taller than the band it fills.

**A composer writes a title, so it grows with it.** `InlineInputSpec.multiline` makes `openInlineInput` build a `textarea` and size it to its own content on every `input` (`scrollHeight`, from `auto` up), capped at `COMPOSER_MAX_HEIGHT` and scrolling past it: a card title is longer than the card-shaped slot it was opened from more often than not, so a fixed box either scrolls the rest of the title out of sight or covers the columns behind it with a field nothing is being typed into. **Enter is the commit key and Shift+Enter is refused, not committed** — Shift+Enter is the way a textarea normally starts a new line and a mermaid card title cannot hold one; committing would drop the break *and* leave the rest of what was typed behind in a field that has gone, so the field stays open with the value the user has.

**A delete asks first, and says what it is taking.** Deleting a card or a column runs `promptForKanbanDelete(subject, consequence)` in `src/urlDialog.ts` — `Cancel`/`Delete`, with Delete in `toolbar-danger`, a note naming what goes and (for a column with cards) how many go with it, Escape and a backdrop click as cancel. It is a dialog rather than a `window.confirm` because a board is the user's document and a delete is undoable: the note says so. `removeKanbanCard` / `removeKanbanColumn` in `src/mermaid-edit.ts` are the pure patchers that answer it — the first removes one card line, the second the column header and every card indented under it, and the second **refuses on a board of one**, because emptying the last column leaves a `kanban` with no columns, which is not a board. Nothing is patched until the answer is `true`, and each is one `setNodeMarkup`, so one undo takes the whole deletion back. The walk that builds a column's header controls is positional (`doc.columns`, `cardElements(svg)` filtered by which band a card's centre is in), which is the same mapping the drag already used, and a card that lands in no band is left alone rather than guessed at — there is no per-card control left to build.

**A field that adds something must not look like one that overwrites something.** `openInlineInput` builds a `div.mermaid-edit-field` around the input rather than the bare input it used to be, because the bare one had no way to carry a shape: a rename gets no `tone` and a `minWidth` of `RENAME_FIELD_WIDTH`, while an add gets `tone: 'new'`, which is what the dashed accent edges in CSS are for, plus a `minWidth` wide enough for a real card title (`NEW_FIELD_WIDTH`). It needs **no words**: it used to print a caption above the field (`New card in <column>`, `New column after <column>`) and that was one thing too many — the place the field was opened from is *drawn in the board*, so the board is the sentence the caption finished, and `tone: 'new'` says "this creates" without a label to keep in step with the source, truncate, or translate. The wrapper owns the geometry and the input is its only child, so the field is one box to place, size and clip to nothing (an absolutely positioned child of a horizontal scroller is placed from the scrolled content, not from the visible box, so the preview's own scroll has to be added back), and `field.remove()` on commit/cancel takes the whole thing with it. The `onAccept` contract is unchanged and still the only place a title can be refused: `true`, `false`, or a *reason* (`usableKanbanLabel`), so a name mermaid cannot read is refused before it is committed, by the same rule the label editor has always used.

**A new board is `insertKanban` end to end.** `buildKanbanSource(columns)` (pure, in `src/mermaid-edit.ts`) turns names into a runnable diagram — `['Todo','Doing']` -> `kanban\n  col1[Todo]\n  col2[Doing]`, with unwritable names dropped, repeats suffixed ` (2)`, and `''` when nothing survives. `promptForKanbanColumns()` in `src/urlDialog.ts` asks for the names, one per line: a textarea, so plain Enter is a *newline* and Ctrl/Cmd+Enter (or Add) confirms. `insertKanbanSource()` in `src/node/mermaid.ts` does the insert as **one** transaction with the mode already set (`openDiagramEditIn()`, shared with `enterDiagramEditMode`), so one undo takes the whole board away; `insertKanbanBoard()` wraps the dialog, the builder and the "none of those names can be used" error, and is what the Insert-menu QAction (`insertKanban` in `MenuCommands`, and the toolbar's Kanban button) calls.

**A kanban title is free text, quoted on the way in.** Mermaid's kanban grammar reuses the flowchart *shape* delimiters inside a `[…]`, and a *quoted* label can hold them — mermaid draws it as the text inside the quotes and nothing else. So `kanbanInnerLabel()` is the single writer used by all three paths — a new card, a new column, a rename — quoting anything in `KANBAN_QUOTE_CHARS` (`[ ] ( ) { } @ > " &`): `Fix (the bug)` is `["Fix (the bug)"]` in the source and `Fix (the bug)` on the board and in the label editor, and the quotes are never anything the user typed or saw. That set is the whole shape syntax, deliberately a **superset** of what real mermaid rejects bare (a 40-diagram sweep says only `]`, `(`, `)`, `}` — `[`, `{`, `<` and `>` all render), because the two extras are ours: an unquoted label holding `@{ … }` is silently eaten as metadata, and one holding `>` renders but `kanbanLabelSpan` refuses it as a shape with no closer — a title the user typed that is not the title the board shows. Do not narrow it. The reader mirrors the writer: `kanbanLabelSpan()` recognises the quoted form *first* (before the shape search, or a bare `"Fix (bug)"` finds its own `(` and maps to `bug`) and returns the **whole quoted run, quotes included**, while `parseKanban` unquotes *and unescapes* it into `label` — so a rename replaces the run and a label already written with quotes keeps them (`kanbanQuotedLabel`; `replaceSpans` writes one spelling over every span, so a mixed board takes the conservative one). **A `"` is carried as an entity, not refused.** Quoting is what makes a raw quote fatal — a quoted label is drawn as the text inside its quotes, so a `"` written raw closes the run it sits in and the rest of the title is read as source (`["He said "hi" (loud)"]` is a real parse error, and mermaid has no backslash escape for it). But the quoted run *does* take an HTML entity: `&quot;` is not a quote to the grammar, survives the run, and mermaid draws it as `"` — so `["He said &quot;hi&quot; (loud)"]` renders the text `He said "hi" (loud)`, and a bare `[&quot;]` is a card whose whole title is one quote. `escapeKanbanEntities` therefore escapes `&` *first* (so a title holding the literal text `&quot;` comes back as that text rather than as a quote) and `"` second, `unescapeKanbanEntities` inverts it in the same order, and both `"` and `&` are in `KANBAN_QUOTE_CHARS` so any title holding either is always written quoted. This was a refusal first, on the belief that a quote was unrepresentable — the belief was never tested, and it was wrong; do not re-derive it from the grammar docs, `src/mermaid-kanban-escaping.test.ts` renders every case through **real** mermaid (every other test here mocks `mermaid.render`, which is how the wrong belief survived) and `scripts/mermaid-label-probe.py --type kanban` walks the escaped spellings through the real gesture, its `spelled_out` check decoding `&quot;`/`&amp;` first because a successful rename legitimately leaves entities in the source.

What quoting cannot carry is refused, not committed: `UNUSABLE_KANBAN_LABEL` is a line break, checked by `usableKanbanLabel()` at the *UI* boundary (the card slot composer's, the menu's `onAccept`, and `openLabelEditor`), which returns `kanbanLabelRefusal()` — `openInlineInput`'s `onAccept` returns `true`, `false`, or a *reason*, and a reason flashes the input red and shows a notice. A committed title mermaid cannot read would leave the board on its last good render with the card the user just typed visible nowhere, which is the whole failure this quoting exists to prevent. The one shape the mapper must still refuse blind is an *unterminated* quote (`["Half open`): nothing says where the label ends, so `label` is `null` and the label is not offered.


The real-engine tests live at the end of `tests/test_window.py` and the shared WebEngine helpers in `tests/mermaid_render.py` (not `test_*.py`, so pytest does not collect it). They render in that module's already-open session window on purpose: a `MainWindow` is a WebEngine page, and the dark-probe plus template sweep already take two, so a module of its own (or a fourth window) turns the suite red for no reason. `QTest` mouse injection never reaches the page, so those tests dispatch JS-synthesised `PointerEvent`s.

## Testing quirks

- Qt must run offscreen headlessly: `QT_QPA_PLATFORM=offscreen` + `QTWEBENGINE_DISABLE_SANDBOX=1`. `tests/conftest.py` sets these via `os.environ.setdefault` *before* importing PySide6 — never import PySide6 before the env is set.
- QtWebEngine `runJavaScript` does **not** await Promises. The packaged-binary smoke test (`EDI_SELFTEST=1`, offscreen) probes sync JS snapshots (`window.__selftest`) and, once the page finishes loading, prints one `SELFTEST {...}` line and exits 0. The app boots a **home screen** (`#app[data-view='home']`) instead of a welcome tab, so the smoke loads the page with `?selftest=1` (backend sets the query when `EDI_SELFTEST=1`); `src/main.ts` checks that flag and opens the Welcome doc so `__selftest.title` still reads `Untitled — Edi`. A 25s watchdog prints `SELFTEST_TIMEOUT` and exits 1. It uses `os._exit` to skip Qt teardown (a wedged renderer can otherwise hang the process and swallow output) and must not depend on async values or the bridge being ready. When `EDI_SELFTEST_OUT` names a file, the same verdict line is also written there before exit — required for the windowed Windows build, which has no attached console (`console=False` makes Python's sys.stdout None); both the Wine build (`scripts/build-windows-wine.sh`, bash) and the desktop `scripts/build-windows.ps1` parse that file instead of stdout. `_run_selftest` first writes a `SELFTEST_BOOTING` heartbeat to that file so a hung smoke can distinguish "still self-extracting / Qt still starting" (no heartbeat) from "Python booted but QtWebEngine never loaded" (stuck on BOOTING). `build-windows-wine.sh` polls the file rather than using a fixed wait — succeeding the moment a `SELFTEST {...}` verdict appears, but under Wine the smoke is fundamentally structural: it stops early (and classifies `SELFTEST_SKIPPED_ENVIRONMENTAL`) the moment the proven Chromium-init crash markers land in the boot log instead of grinding the **20 min budget** (`EDI_SMOKE_BUDGET_MIN` overrides), and hard-fails only on extraction/DLL-load/anomaly evidence. `build-windows.ps1` does the same on a real Windows desktop with a **3 min budget** (same `EDI_SMOKE_BUDGET_MIN` override). Run 2 hung; runs 3+ exit with code `-1`, which is the windowed bootloader relaying the **child Python process's** nonzero exit — NOT a bootloader/corrupt-archive abort, and `%TEMP%\_MEI*` was a complete extraction all along (the old "partial extract: 62 files" DIAG counted only top-level entries). When the console twin shows Python booting, the actual packaged-binary failure mode is a DLL load error (e.g. `ImportError: DLL load failed while importing QtWebEngineCore: The specified module could not be found.`). Cause (proven on GitLab's former `saas-windows-medium-amd64` runner, since replaced by the Wine build): all 20 Qt6 DLLs — every WebEngineCore companion AND Qt6WebEngineCore.dll itself — are present in the bundle; the load still fails because **Qt6WebEngineCore.dll has hard static imports of `dcomp.dll` (DWM compositor) and `bthprops.cpl` (Bluetooth shell) that Server-SKU runners do not have** (proven by parsing the win_amd64 wheel's import table with `pefile`, and by PyInstaller warning on exactly those two — everything else, incl. `msvcp140.dll`, resolves from System32). Linux pulls only the Qt libs via ELF `DT_NEEDED` so it works; and `dcomp.dll`/`bthprops.cpl` exist on normal Windows 10/11 desktops. That was necessary but NOT sufficient: the exes built by that runner (and by early Wine builds here) also shipped with **zero Qt plugins** because **Wine lacks System32's `icuuc.dll`/`icuin.dll`**, which `Qt6Core.dll` hard-imports (20 `ucnv_*` symbols, proven via `pefile` and a wine loader trace `err:module:import_dll Library icuuc.dll ... not found`). PyInstaller 6.22's Qt hooks discover the Qt install by importing `PySide6.QtCore` in an isolated subprocess; with ICU unresolvable that probe failed, the hooks found no plugins, and the onefile booted with "no Qt platform plugin could be initialized" on any real desktop. Nobody ships the DLL: the win_amd64 wheels carry only `resources/icudtl.dat`, official Qt 6.11.1 bin has no ICU DLL, and `icuuc.dll` is a Windows system DLL (present in every real System32 ≥ 1703; Wine bundles it only since the **11.5 development line** — so `Dockerfile.wine` installs **winehq-staging**, never wine-stable 11.0). The fix (2026-09): the build copies Wine's bundled ICU (`/opt/wine-*/lib/wine/x86_64-windows/icu*.dll`) into the prefix's `site-packages/PySide6/` so the hook probe succeeds and the plugins get collected canonically; `edi.spec`'s win32 branch then force-appends those ICU DLLs to the bundle (deduped, like the WebEngine companions) so the exe is self-contained even on no-ICU Windows. Both `build-windows-wine.sh` and `build-windows.ps1` therefore probe/make the venv's QtWebEngineCore import work **before** the frozen smoke (probe fail ⇒ `SELFTEST_SKIPPED_ENVIRONMENTAL`, exit 0, packaging proceeds; the `.ps1` desktop path stages System32's ICU into the venv the same way and still runs the FULL render smoke on real Windows). Under Wine specifically, the frozen onefile boots — extraction + Python + Qt init are proven — but QtWebEngine's Chromium then FATALs during init (`network_change_notifier_win.cc`: `WSALookupServiceBegin failed with: 8`; `hwnd_util.cc:65]: 1400`) and Wine parks an invisible `winedbg` dialog, so the script bounds the smoke, stops early when those markers land, kills the process tree, and classifies the crash `SELFTEST_SKIPPED_ENVIRONMENTAL` — while still hard-failing on extraction errors / `DLL load failed` / missing plugins (the CArchive structural check, 4a, is the load-bearing regression gate for the pluginless-bundle bug). The probe must run under `$ErrorActionPreference='Continue'` with `2>&1` capture and then restore EAP — Windows PowerShell 5.1 promotes native-command stderr to a terminating `NativeCommandError` when EAP is 'Stop' (that aborted the job before the skip logic ran on the first attempt). `edi.spec`'s win32 branch still explicitly appends the WebEngine companion set (`Qt6WebEngineCore/Qt6WebEngineWidgets/Qt6Qml/Qt6Quick/Qt6QuickWidgets/Qt6QmlModels/Qt6QmlWorkerscript/Qt6Positioning/Qt6WebChannel/Qt6Network/Qt6PrintSupport`) to `a.binaries` as `(dest, src, 'BINARY')`, deduped against `b[0]` dests already collected. Note the bundle root holds NO Qt DLLs — they extract to the `PySide6/` subdirectory (System + python DLLs sit at the root; the msvcp140 family is never collected because PyInstaller excludes everything resolved under `C:\Windows`, which is fine — System32's copy loads). `run_edi.py` dumps the bundle inventory and, on import failure, a **PE import-table lint** of the failing Qt module (`[selftest] OK <name> -> bundle|System32` / `MISSING <name>`) under `EDI_SELFTEST`. The windowed bootloader (`runw.exe`, `console=False`) swallows the fatal message into an invisible dialog; `edi.spec` therefore also builds a **console twin `Edi-selftest.exe`** (win32 branch only, shares Analysis/pyz, ~+30s pack) that `build-windows.ps1` smoke-tests instead: `Start-Process -RedirectStandardOutput/-RedirectStandardError` captures the real `Error extracting <entry>: <errno>` line and dumps it into the job log (still also parses `EDI_SELFTEST_OUT`). The twin is deleted before the artifact phase so the `dist-app/Edi-*.exe` glob ships the versioned onefile **and** the installer (`Edi-<v>-win64-setup.exe`) — the NSIS installer is built by the same Windows job (native Windows makensis, `choco install nsis`; no Wine involved). The Path-quirks lesson from the old runner still applies: makensis resolves relative `File`/`OutFile` paths against the **script's** directory, not the CWD, so `build-windows-wine.sh` passes `-DSETUPEXE`/`-DICO`/`-DOUTEXE` as **absolute** paths (Linux makensis also takes `-D`, not `/D`); `edi.nsi` exposes an optional `OUTEXE` define so the output lands in the checkout root, not `packaging/`. `build-windows.ps1` can still build one on a real Windows desktop (`packaging/edi.nsi` stays desktop-compatible).
- `pyproject.toml` sets `pythonpath=["."]`, so run pytest from the repo root; running it elsewhere breaks `import backend`.
- QtWebEngine segfaults at interpreter exit in headless/container pytest runs (tests pass, job fails with exit 139). `tests/conftest.py` `pytest_sessionfinish` registers an `atexit` `os._exit` that passes pytest's real exit status and skips Qt teardown. Keep the handler registered only at session end, not at import, so real crashes mid-run still propagate as signals.
- The onefile binary self-extracts ~450 MB to `$TMPDIR` on every launch. `/tmp` is often a small tmpfs, so the smoke tests (`build-pyzip.sh`, CI `build` job) point `TMPDIR` at a disk-backed `build/tmp`. A full write there surfaces as `Failed to extract ...: decompression resulted in return code -1` — that return code is the bootloader's `Z_ERRNO`, set only when `fwrite` fails while unpacking (a corrupt archive would show -2/-3/-4), so it means temp space ran out, not a broken binary. The selftest `os._exit`s without Qt teardown, so a QtWebEngine subprocess can outlive the parent and re-launch the onefile bootloader; `build-pyzip.sh` therefore waits for `dist-app/edi` processes to exit before removing the smoke temp dir, or a late one fails with `Could not create temporary directory!`.

## Distribution (hard-won constraints — do not break)

- The shipped binary MUST be built on **Ubuntu 22.04 (glibc 2.35)** so it runs on older desktop Linux. `scripts/build-pyzip.sh` pins everything inside Docker for this; host-built binaries are not portable and must not be shipped.
- **`libstdc++.so.6` and `libgbm.so.1` must never be bundled** (`edi.spec` `GL_HOST_DEPS` filters them out). Bundling the 22.04 copies breaks host Mesa/LLVM loading: libstdc++ crashes with `GLIBCXX_3.4.32 not found`, and libgbm (Mesa's buffer manager) makes QtWebEngine's GPU process print `did not find extension DRI_Mesa version 1` / `EGL: Failed to initialize GBM device` and fall back to software rendering on any host whose Mesa is newer than 22.04's.
- **Qt bundle pruning in `edi.spec`**: Edi uses only the QtWebEngine *widgets* API, so `excludes=['PySide6.QtQml', 'PySide6.QtQuick']` keeps hook-PySide6.QtQml from firing — otherwise it drags in the entire `qml/` tree (~4,850 plugin files) plus every Qt lib those plugins reference (Qt3D, QtQuick3D, QtCharts, QtGraphs, QtVirtualKeyboard, ...). The libQt6Qml/libQt6Quick shared libs WebEngineCore genuinely links against are still pulled by binary dependency analysis, so this is safe. `QT_DEAD_PREFIXES` additionally drops the on-screen-virtual-keyboard input-context plugin and its libs (match the soname-form dest too — PyInstaller emits both `PySide6/Qt/lib/...` and top-level `libQt6...` entries). Verify with `rg -c 'libQt6' build/edi/PKG-00.toc` (expect ~100, not 468) and the smoke test.
- **PyInstaller archive compression**: the CArchive (PKG) step defaults to zlib **level 9**, which makes the onefile pack step dominate build time. Build with `PYINSTALLER_ZLIB_COMPRESSION_LEVEL=1` (set in `Dockerfile.pyzip` and the CI `build-linux` job) — ~3x faster pack; the binary grows ~18 MiB but every release wrapper (.deb/.rpm/.tar.gz/.AppImage) recompresses anyway.
- **Frontend must be a single JS bundle — no runtime `import()`**: the app ships to QtWebEngine as `dist/index.html` under `file://`, and QtWebEngine intermittently fails runtime dynamic module fetches under load (`Uncaught (in promise) TypeError: Failed to fetch dynamically imported module`). That was the root cause of the chronically flaky `tests/test_mermaid_templates.py` (mermaid's internal `mermaid.core.js` split chunk failing) and can hit real users as "Mermaid render error". `vite.config.ts` therefore sets `build.rolldownOptions.output.codeSplitting: false` — one ~5.4 MB minified bundle, no async chunks (the remaining `import(` in the minified output is ESLint-mode regex text / an `import.meta.resolve` feature-detect). Do NOT re-enable code-splitting for "perf" — the depot is local disk; the lazy-loading it buys has cost intermittent renderer errors.
- The app icon (`scripts/assets/app-icon.png`) is generated from `scripts/generate-icon.mjs` and bundled via `edi.spec` `datas`. `backend/window.py` `load_app_icon()` guards `sys._MEIPASS` (built binary vs. source run) — keep that guard. The about dialog reuses the same artwork (`load_about_logo()` scales `scripts/assets/app-icon.png`); the old `assets/edi-logo.png` was deleted — do not reintroduce a separate logo. The same script now also writes `app-icon.ico` (16–256, for the Windows EXE resource/installer) and `app-icon.icns` (16–1024, for the macOS BUNDLE); both are gitignored build artifacts regenerated before each native pyinstaller run.
- **Windows/macOS binaries**: PyInstaller cannot cross-compile, so each OS's bundle is produced on a machine that provides that OS's runtime. Windows is now built on Linux via a WineHQ container (see the Wine build bullet); macOS still MUST build on macOS. `edi.spec` branches on `sys.platform` over a shared `Analysis` (datas + QtQml/QtQuick excludes are platform-independent): only the Linux branch applies `GL_HOST_DEPS` / `QT_DEAD_PREFIXES` and keeps the lowercase `edi` EXE name; the `win32` branch names the EXE `Edi`, attaches `scripts/assets/app-icon.ico` and a `VSVersionInfo` (version parsed from `backend/__init__.py` at spec time so it cannot drift from the tag); the `darwin` branch makes `Edi` + a `BUNDLE` into `Edi.app` with an Info.plist declaring the icon and `bundle_identifier=com.mrdanpsmith.edi`.
- **Windows CI builds on real Windows** (the `build-windows` job, `runs-on: windows-2025`, 45m timeout, `needs: frontend`). It *used* to run on `ubuntu-24.04` inside the `ghcr.io/<owner>/edi-wine-builder:jammy` image (`Dockerfile.wine` + `scripts/build-windows-wine.sh`), emulating the target; that path cost 30-50m a release and could never render, and it is gone from CI. What actually made it expensive: a Wine prefix has to be built from GUI installers under a synthetic X display (wineboot + VC++ redistributable + the Windows Python installer ≈ 26m cold), and then PyInstaller's walk of the ~1.5 GB PySide6 tree goes through Wine's NT path layer, so the same build that takes ~3m on a good day took 40m on a contended one. Wine can also never import `QtWebEngineCore` (its Chromium FATALs in `network_change_notifier_win.cc`), so its smoke was permanently downgraded to a structural check. The native path removes all three problems at once. The reason this was ever Wine at all is that the *reason macOS builds natively* — "PyInstaller cannot cross-compile" — applies verbatim to Windows; the difference is only that Windows had a working emulation hack, and the hack was the bug. GitHub-hosted Windows runners are **pre-warmed** (measured: 4s to provision, 0s "Set up job"), so this is NOT the per-job VM spin-up that made GitLab's Windows runners cost minutes — that was the objection worth checking before switching, and the measurement cleared it. The job is three steps and mirrors the old Wine job's shape: consume the `edi-web` artifact (so **no Node/npm**), run `scripts/build-windows.ps1` (venv + `pip` + PyInstaller + the full offscreen smoke, staging System32's ICU into the venv), then the structural check, then native `makensis` with **absolute** `-D` defines (makensis resolves relative `File`/`OutFile` against the *script's* directory, not the CWD), uploading `dist-app/Edi-*.exe` as `edi-win`. The selftest console twin is deleted before the upload so the glob ships exactly the versioned onefile + the installer.
- **The structural bundle check is one shared file, and it is the load-bearing regression gate.** `scripts/check_bundle_contents.py` asserts that `qwindows.dll`, `qoffscreen.dll`, `qjpeg.dll`, `icuuc.dll` and `icuin.dll` are all in the CArchive (CArchiveReader is pure stdlib + PyInstaller, so it reads the `.exe` with no render, no X display and no GPU). The pluginless-bundle defect dies here: the Qt hooks stop collecting, PyInstaller still reports success and still produces an `.exe`, and the only symptom is a crash on a machine lacking the DLLs. It has to be separate from the smoke because **the smoke can be skipped as environmental** — on a host that cannot import `QtWebEngineCore` the frozen render proves nothing about the bundle, so this check is the one that still runs. Both the native job and `build-windows-wine.sh` call that same file rather than each carrying its own list, precisely because two copies are two chances to let that defect through.
- **`scripts/build-windows.ps1` is the Windows build, and the smoke is real here.** It is a host-capability probe on the freshly-installed venv, then the frozen smoke of the `Edi-selftest.exe` console twin (the shipped `Edi.exe` is `runw.exe`/windowed and swallows extraction errors into an invisible dialog, so the twin is what puts `Error extracting <entry>: <errno>` in the log), polled against a deadline rather than a fixed wait, printing the bootloader stdout/stderr that `runw.exe` would hide. The verdict is parsed from `EDI_SELFTEST_OUT` because no console is attached to the job, with `EDI_SELFTEST_BOOTING` as a heartbeat so a hang can be distinguished from a slow boot. A host that cannot import `QtWebEngineCore` is classified `SELFTEST_SKIPPED_ENVIRONMENTAL` and the build continues — a client-SKU `windows-2025` runner is *not* such a host (the Server-SKU case was GitLab's SaaS Windows runners, which lack `dcomp.dll`/`bthprops.cpl`), so this should be a genuine render verdict. The `.ps1` is also still the desktop path; nothing about it is CI-specific.
- **`Dockerfile.wine`, `scripts/build-windows-wine.sh` and the `edi-wine-builder` image are the local/legacy Wine path, not CI.** The script is still a usable *local* route (`docker run`s the image with the checkout mounted, prefix cached in `build/wine-prefix`), and the image is still built by `images.yml`. It is no longer on any release path, so it can be deleted without touching the release DAG; `requirements-win.txt` is still the shared pin list. The Wine build's own quirks (the `winehq-staging` pin, the bundled-ICU staging, `gui()` retries, the `SELFTEST_SKIPPED_ENVIRONMENTAL` classification) are documented here only so they are not mistaken for live CI behaviour while the files exist.

- **macOS CI runs on GitHub Actions' free arm64 `macos-15` runners** (the `build-macos` job, gated to `v*` tags / manual validation like the other binary jobs). `scripts/build-macos.sh` (Darwin-only; brew-installs Node 20+/Python 3.10+ as needed) mirrors the Linux steps into `dist-app/Edi.app`, ad-hoc code-signs it (`codesign --force --deep -s -`, arm64 will not launch unsigned), smoke-tests the bundle binary, then wraps it into `dist-app/Edi-<ver>-macos-arm64.dmg` (drag-to-Applications, `Applications` symlink). Apple Silicon only; unsigned/not-notarized (no Apple Developer account), so Gatekeeper warns on first open — accepted, documented tradeoff; don't add signing stubs that imply Developer-ID signing works. The job consumes the `edi-web` artifact exactly as the Linux and Windows jobs do and **asserts** `dist/index.html` + both generated icon variants rather than building them: `build-macos.sh` used to run its own `npm ci` / `npm run build` / `node scripts/generate-icon.mjs`, which meant the `.app` shipped a second, untested build of the UI, the generated `.icns` in the `edi-web` artifact had no consumer at all, and nothing enforced the two were the same (the docs claimed "byte-identical" while also saying macOS rebuilt it). The assert is a hard failure with the one command that fixes it — same shape as `build-windows.ps1`'s two preconditions — and there is deliberately **no rebuild fallback**: a script that quietly regenerates what it was told to consume turns a broken artifact download into a green build of something else, which is the failure mode worth refusing to have. So the frontend and the icons are built **once**, in the `frontend` job, and everything downstream is a consumer.
- `PySide6==6.11.1` and other pins live in `requirements.txt`; the Windows build mirrors them (`PySide6==6.11.1` + `pyinstaller==6.22.0` + `defusedxml` in `requirements-win.txt`, consumed by Dockerfile.wine and `scripts/build-windows.ps1`); keep PySide6 pinned (Qt releases break the WebEngine hooks).
- `backend/tables.py` (Insert → Spreadsheet) parses ODS/XLSX XML with **`defusedxml`** as a drop-in for `xml.etree.ElementTree` — plain ElementTree is XML-bomb vulnerable on user-opened files, and bandit greets it with a Medium finding. It is a runtime import, so every PyInstaller build venv must install it, not just the dev/CI venv: `Dockerfile.pyzip`, `Dockerfile.wine`, `scripts/build-windows.ps1` and `scripts/build-macos.sh` each pin it explicitly alongside PySide6 (PyInstaller collects it automatically once it's importable).

## CI (GitHub Actions — `.github/workflows/ci.yml` + `release.yml` + `images.yml`)

- Two workflows, two pipelines: **`ci.yml` (name `CI`)** is the normal commit pipeline — runs on every `pull_request` and on every push to `main` / `release/**` branches, and only runs the testing phases (`frontend` + `test`), never binaries or releases. **`release.yml` (name `Release`)** is the full tag-gated DAG (`v*` tags or manual `workflow_dispatch`, `VER` defaulting to `0.0.0`) — the same quality gate plus the platform builds, packaging, and publishing. The `frontend`/`test` job bodies are **deliberately mirrored** across both files (each pipeline stays self-contained); that's why `.jscpd.json` ignores `**/.github/workflows/**`. The single `concurrency: ci-${{ github.ref }}` covers both events on purpose: a PR's `github.ref` is `refs/pull/N/merge`, so a new push cancels the superseded run without ever colliding with the `refs/heads/main` group, and a merge still runs the push job.

- Coverage stays **cobertura** — that is load-bearing, not incidental: the `badges` job reads the two reports' `line-rate`s and the `Publish coverage summary` step tails both runners' output, so the two reporters must keep emitting Cobertura and the two paths must keep their names. `npm run coverage` → `coverage/cobertura-coverage.xml` (Vitest v8), pytest → `coverage-py/cobertura-coverage.xml` (pytest-cov 7 has no `cobertura` reporter; `xml:...` output is Cobertura). Each side also emits an **HTML** report to a sibling `index.html` (`coverage/`, `coverage-py/html` — pytest-cov's `html:...` is pinned under `coverage-py/` so the whole thing is one gitignored tree), and the `test` job uploads `coverage/` + `coverage-py/` wholesale as the **`coverage-report`** artifact (`retention-days: 30`, `if-no-files-found: error`, default branch only) so a run's page offers the browsable report. That is the whole reason the artifact ships the *directories* and not the two XML paths: the badges job reads the two Cobertura files out of the same download, so one upload serves both consumers, and widening the path is what the HTML report required. The frontend denominator is **every `src/**` file**: Vitest 4 removed `coverage.all`, and the v8 provider globs `coverage.include` after a full run and reports what it never loaded, so a module no test imports lands at 0% (verified with a throwaway `src/zzNeverImportedProbe.ts`: 63 → 64 classes, row at 0%). Do not "fix" that by adding `all: true` — the key is gone and the setting is silently inert. Two consequences of the same path: a single-file re-run skips it (`cleanOnRerun`), so `npm run coverage` is the report that counts, and `src/test-setup.ts` is missing by accident rather than by rule (the runner loads it uninstrumented, so it is in neither bucket — and `coverage.exclude` must stay unset, since replacing the default list would pull all 53 `*.test.ts` files into the report).
- **GitHub's built-in coverage dashboard is not available to this repository, and its upload steps are deliberately absent.** `actions/upload-code-coverage@v1` worked exactly as documented — it reached the API and got `Coverage upload failed (HTTP 404)` — because *GitHub Code Quality is a paid product, GA since 2026-07-20 for GitHub Team and GitHub Enterprise Cloud only*. A Free/Pro personal repo is not an eligible plan, so there is no Settings → Security → Code quality page to find, the API endpoint does not exist for the repo, and every upload is a permanent 404 (a no-op warning, since `fail-on-error: 'false'` was already set). Do not re-add those two steps, the `permissions: code-quality: write`, or the `if:` that went with them on the strength of a fix here: the only fix is moving the repo into an organisation on a paid plan, and 404 is the *expected* result of not having done that. What replaced them is plan-independent — the `Publish coverage summary` job summary (the per-run human-readable twin) and the README's own badges, below. If the repo ever does move to a paid plan, the docs' shape is two steps (one per language, `file`/`language`/`label`) plus the job-level permission, and the `pull_request` trigger `ci.yml` already gained is what puts a PR's numbers on its own head SHA rather than the merge commit.
- The README's badge row is the other consumer of those two Cobertura paths, and it is the one that needed machinery of its own: a live coverage badge has to be fed from somewhere, and the obvious somewhere — GitHub's own coverage API — is not an option twice over (it has no badge URL, and it is not available on this plan at all). It is fed from a dedicated **`badges` branch** — the `badges` job in `ci.yml` reads both `line-rate`s, writes `coverage-ts.json` / `coverage-py.json` (`{schemaVersion, label, message, color}` — the `color` is what turns the badge red on its own at <90/80/70%) and force-pushes them, and the README points shields.io at the raw files with `/endpoint`. Which shields endpoint matters here, and the obvious one is a trap: the row uses **`/endpoint`**, not `/badge/dynamic/json`, even though both take a `url` and the job writes the same `{schemaVersion, label, message, color}` document — `dynamic/json` requires a *second* parameter, `query` (a JSONPath selector), and returns **only the message**, with its label and colour coming *only* from the badge URL's own query string. Omit `query` and the badge renders shields' `invalid query parameter: query` instead of a number; supply it and the two coverage badges can no longer change colour on their own. `/endpoint` takes `url` alone and reads label *and* colour out of the document, which is what makes the `color` field in those files worth writing at all. Four decisions are load-bearing: the branch is **one force-pushed commit with no history** (it is data, not history, so a re-run can never conflict with itself and no merge/queue step is needed); publishing is **its own job** so `contents: write` never sits in `test`, which runs the test suite — the reports cross the boundary as the `coverage-report` artifact instead, which is also why the job needs neither the builder image nor Node; the job's `if:` is **default branch only**, the same condition as the artifact step that feeds it — a badge should read main, and a fork PR's token is read-only anyway, so the push would fail; and the **job exists in `ci.yml` only**, which is the one deliberate divergence from the mirrored `test` bodies (a tag or `workflow_dispatch` run has no branch to publish a baseline for, so `release.yml` carries a pointer comment instead of a job that could never run). `raw.githubusercontent.com` plus shields both cache, so a badge can trail the newest run by a few minutes. The license badge is a **static** `GPL--3.0--or--later` rather than the auto-detected `github/license` one on purpose: the auto badge reads the plain GPLv3 `LICENSE` text, which is byte-identical for the `-only` and `-or-later` variants, and would contradict the README's own "GPLv3 (or later)".
- QtWebEngine hangs in containers with small `/dev/shm` / no GPU: set `QTWEBENGINE_CHROMIUM_FLAGS="--disable-dev-shm-usage --disable-gpu"` (and `QTWEBENGINE_DISABLE_SANDBOX=1`) for any headless Qt run — the workflows set these globally.
- `test` needs `dist/` for pytest (backend tests load `dist/index.html`); the `frontend` job builds it and `test` downloads the artifact.
- Compute-conscious CI setup: most jobs run **inside** a prebuilt **builder image** (`ghcr.io/<owner>/edi-builder:jammy`, built from `Dockerfile.ci` by `images.yml` — on main when `Dockerfile.ci`/`requirements.txt`/`.github/workflows/images.yml` change, never on tags, and manually via `workflow_dispatch`; run it once manually after a fresh import so ghcr has the images). It bakes the ~30 Qt runtime libs, Node 22, and a venv at `/opt/edi/venv` (PySide6==6.11.1, pyinstaller==6.22.0, pytest, pytest-qt, pytest-cov, defusedxml, bandit, pip-audit). Jobs use it as a `container:` and link the venv with `ln -s /opt/edi/venv .venv` (package-linux.sh hardcodes `$ROOT/.venv`) and `npm ci` where needed. The `build-windows` job is on none of this — it runs on a GitHub-hosted `windows-2025` runner and `pip install`s its own venv, so it needs neither image. A second image (`ghcr.io/<owner>/edi-wine-builder:jammy` from `Dockerfile.wine`) is still built by `images.yml` for the **local/legacy** Wine route only (triggered on `Dockerfile.wine`/`requirements-win.txt` changes), and no release job consumes it. **Never pip-install into the baked venvs at job time** — they're read-only image layers; bake changes into the images. `images.yml` must use a `docker-container` buildx driver (the default `docker` driver errors with "Cache export is not supported for the docker driver" on `--cache-to type=registry`) and must pass `-f Dockerfile.ci` explicitly — the repo root also has a plain `Dockerfile` (the app's container image: node frontend stage + `ubuntu:26.04` runtime), which buildx builds by default and would produce a node-less image with the venv at `/app/.venv` instead of `/opt/edi/venv`. Jobs pull the ghcr images as **public packages**, so no auth and no fork-registry failure.
- npm caching: `actions/setup-node` `cache: npm` (frontend + macOS jobs) — never `node_modules/` or `.venv/` (they exceed GitHub's cache cap and caused misses; `npm ci` deletes node_modules anyway). The Linux/Windows binary jobs need no Node at all: they consume the `edi-web` artifacts (macOS is the exception — `build-macos.sh` does its own `npm ci`).
- The quality gate is split over two jobs in both pipelines: `frontend` runs lint + typecheck + dupcheck + the production build (producing `dist/` + `.ico/.icns`); `test` runs vitest coverage + bandit + pytest + the two coverage uploads, then the network audits (`npm run audit`, `.venv/bin/pip-audit -r requirements.txt`) last so a transient network failure doesn't burn the deterministic gate. Keep local `npm run check` as the full gate.
- Binary jobs are gated to `v*` tags (or manual `workflow_dispatch`, where `VER` falls back to `0.0.0` for validation): `build-linux` runs in the jammy container (the glibc 2.35 pin), `build-windows` natively on a GitHub-hosted `windows-2025` runner, `build-macos` on a free arm64 `macos-15` runner. The tradeoff stands: a pyinstaller/Mac regression surfaces only on a tag or a manual run.
- Release-pipeline DAG (`.github/workflows/release.yml`): `frontend` → `test` (dist artifact); `frontend` → `build-linux` + `build-windows` + `build-macos` in parallel, and **all three consume that one `edi-web` artifact and none of them recompiles the frontend** — the platform builds need no Node at all, which is the whole point: the `.deb`/`.rpm`/`.AppImage`/`.exe`/`.app` all ship the same `dist/` the `test` job just validated → `package-linux` (`needs: build-linux`, never recompiles — it wraps the onefile) → `release` (`needs: [test, package-linux, build-windows, build-macos]`; **`test` is in that list because a gate nothing waits on is not a gate** — it used to run beside the builds with its result discarded, so a red `pytest` still published binaries). Artifact downloads are scoped by name to exactly what each job consumes (each build job pulls only the small `edi-web` artifact, never the ~193 MB onefile; `release` pulls only the four packaged files + the .exe + the .dmg).
- `release` publishes via `gh release create <tag> file...` on `v*` tags, authenticated by the runner's built-in `GITHUB_TOKEN` (job `permissions: contents: write`). It refuses to run if `$GITHUB_REF_NAME != v$(version.sh current)`. **Do not glob `dist-app/...` in the release job**: `upload-artifact` v4 flattens wildcard uploads (paths are preserved only "after the first wildcard"; multi-path wildcard uploads root at their LCA), so artifacts unzip flat at the artifact root — the win/mac files even lose their `Edi-` prefix. The job downloads all three artifacts into `artifacts/` and `find`-enumerates them (fails loudly if none landed).
- Linux dock/taskbar icon comes from a `.desktop` file (not the window icon), so the bare binary shows a generic gear without one. `scripts/install-desktop.sh` installs `~/.local/share/icons/hicolor/512x512/apps/edi.png` + `~/.local/share/applications/edi.desktop` (template `scripts/assets/edi.desktop`, `Exec` substituted); `app.setDesktopFileName("edi")` in `backend/main.py` hints the WM to match it.
- Release artifacts are versioned and wrapped: the CI `package` job (v* tags only) runs `scripts/package-linux.sh`, which wraps the already-built onefile (never recompiles; inherits the glibc 2.35 build) into `edi_<v>_amd64.deb`, `edi-<v>-1.x86_64.rpm`, `edi-<v>-linux-x86_64.tar.gz`, `Edi-<v>-x86_64.AppImage`. The `release` job publishes everything via `gh release create <tag> file...` (multi-file is supported) and refuses to run if `$GITHUB_REF_NAME != v$(version.sh current)`. `rpm` and `file` (required by appimagetool and rpm's brp scripts) are baked into the builder image.
- Runtime dependency lists live in `scripts/package-linux.sh`: `DEB_DEPENDS` (Debian names) and `RPM_REQUIRES` (different names — e.g. `libnss3`→`nss`, `libasound2`→`alsa-lib`, `libpulse0`→`pulseaudio-libs`, `libgssapi-krb5-2` merges into `krb5-libs`). The .deb is validated on a clean `ubuntu:22.04` container (apt resolves Depends and `EDI_SELFTEST=1` runs); the .rpm needs a Fedora/Rocky box for the full dnf resolution test (this sandbox cannot reach `mirrors.fedoraproject.org`). `%global _debug_package 0` in `packaging/edi.spec.in` stops rpmbuild's find-debuginfo from choking on the prebuilt binary; `rpmbuild` needs `--define "_dbpath <dir>"` when building as non-root.
- `dpkg-deb` output is forced to `-Zxz` (`packaging/control.in`) so old apt can read it; the hicolor icon set (16–512) is scaled from the 1024 source with a PySide6 `QImage` snippet (headless, no QApplication needed). AppImage uses `appimagetool` pinned to `1.9.1` (fallback: `continuous`), run with `APPIMAGE_EXTRACT_AND_RUN=1` (no FUSE in CI) from the stage dir so the output lands there. The AppImage's squashfs zstd level is lowered to 1 via `--mksquashfs-opt -Xcompression-level 1` — mksquashfs's default level 15 is slow on the ~180 MB payload for a few percent less size.
