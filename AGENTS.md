# AGENTS.md

Edi is a markdown editor. Frontend: CodeMirror 6 + Mermaid + spreadsheet formulas (TypeScript/Vite) compiled to a static `dist/`. Backend: Python 3 + PySide6/QtWebEngine. A native `QWebEngineView` hosts `dist/index.html`; the page talks to Python via `QWebChannel` (`backend/bridge.py`). This is NOT a plain web app — `npm run dev` runs only the Vite server; the real app is Python.

## Key commands

- `npm run check` — typecheck + eslint + frontend unit tests (Vitest). Run this before backend work.
- `npm run build` — node version check + `tsc --noEmit` + Vite build into `dist/`.
- `.venv/bin/pytest tests/` — backend tests. **Requires `dist/` to exist first** (run `npm run build`); `tests/test_window.py` fails fast with a clear message otherwise. Also reports coverage (pytest-cov, from `pyproject.toml` `addopts`): term-missing table on stdout + Cobertura XML at `coverage-py/cobertura-coverage.xml` (needs pytest-cov installed; it's in `requirements.txt`).
- `./scripts/install-deps.sh` — one-time setup: `.venv/` (PySide6 + pytest + pytest-cov) + `npm install` + generates `scripts/assets/app-icon.png` via `node scripts/generate-icon.mjs`.
- `./scripts/build-pyzip.sh` — builds `dist-app/edi` (single-file binary) inside an Ubuntu 22.04 Docker container, smoke-tested offscreen.

## Testing quirks

- Qt must run offscreen headlessly: `QT_QPA_PLATFORM=offscreen` + `QTWEBENGINE_DISABLE_SANDBOX=1`. `tests/conftest.py` sets these via `os.environ.setdefault` *before* importing PySide6 — never import PySide6 before the env is set.
- QtWebEngine `runJavaScript` does **not** await Promises. The packaged-binary smoke test (`EDI_SELFTEST=1`, offscreen) probes sync JS snapshots (`window.__selftest`) and, once the page finishes loading, prints one `SELFTEST {...}` line and exits 0. A 25s watchdog prints `SELFTEST_TIMEOUT` and exits 1. It uses `os._exit` to skip Qt teardown (a wedged renderer can otherwise hang the process and swallow output) and must not depend on async values or the bridge being ready. When `EDI_SELFTEST_OUT` names a file, the same verdict line is also written there before exit — required for the Windows GUI build, which has no attached console (`console=False` makes Python's sys.stdout None); the Windows build job parses that file instead of stdout. `_run_selftest` first writes a `SELFTEST_BOOTING` heartbeat to that file so a hung smoke can distinguish "still self-extracting / Qt still starting" (no heartbeat) from "Python booted but QtWebEngine never loaded" (stuck on BOOTING). `build-windows.ps1` polls the file rather than using a fixed wait, succeeding the moment a `SELFTEST {...}` verdict appears and failing with a phase-specific message after a **3 min budget** (`EDI_SMOKE_BUDGET_MIN` overrides; the post-boot phase is already bounded by the 25 s watchdog, so a hang can only be pre-boot extraction — budget hangs are not retried, fast no-verdict exits are retried once). Run 2 hung; runs 3+ exit with code `-1`, which is the windowed bootloader relaying the **child Python process's** nonzero exit — NOT a bootloader/corrupt-archive abort, and `%TEMP%\_MEI*` was a complete extraction all along (the old "partial extract: 62 files" DIAG counted only top-level entries). When the console twin shows Python booting, the actual packaged-binary failure mode is a DLL load error (e.g. `ImportError: DLL load failed while importing QtWebEngineCore: The specified module could not be found.`). Cause (confirmed on GitLab's `saas-windows-medium-amd64` runner): all 20 Qt6 DLLs — every WebEngineCore companion AND Qt6WebEngineCore.dll itself — are present in the bundle; the load still fails because **Qt6WebEngineCore.dll has hard static imports of `dcomp.dll` (DWM compositor) and `bthprops.cpl` (Bluetooth shell) that Server-SKU runners do not have** (proven by parsing the win_amd64 wheel's import table with `pefile`, and by PyInstaller warning on exactly those two — everything else, incl. `msvcp140.dll`, resolves from System32). Linux pulls only the Qt libs via ELF `DT_NEEDED` so it works; and `dcomp.dll`/`bthprops.cpl` exist on normal Windows 10/11 desktops, so shipping is unaffected. No bundle can ever run QtWebEngine on that runner — even plain `python -c "import PySide6.QtWebEngineCore"` fails identically there, and the missing files cannot be legitimately redistributed. `build-windows.ps1` therefore probes the venv copy of QtWebEngineCore **before** the frozen smoke: probe fail ⇒ write `SELFTEST_SKIPPED_ENVIRONMENTAL` to `EDI_SELFTEST_OUT` and skip the frozen smoke (exit 0, packaging proceeds); probe pass ⇒ full smoke still runs (as it does on any normal desktop). The probe must run under `$ErrorActionPreference='Continue'` with `2>&1` capture and then restore EAP — Windows PowerShell 5.1 promotes native-command stderr to a terminating `NativeCommandError` when EAP is 'Stop' (that aborted the job before the skip logic ran on the first attempt). `edi.spec`'s win32 branch still explicitly appends the WebEngine companion set (`Qt6WebEngineCore/Qt6WebEngineWidgets/Qt6Qml/Qt6Quick/Qt6QuickWidgets/Qt6QmlModels/Qt6QmlWorkerscript/Qt6Positioning/Qt6WebChannel/Qt6Network/Qt6PrintSupport`) to `a.binaries` as `(dest, src, 'BINARY')`, deduped against `b[0]` dests already collected. Note the bundle root holds NO Qt DLLs — they extract to the `PySide6/` subdirectory (System + python DLLs sit at the root; the msvcp140 family is never collected because PyInstaller excludes everything resolved under `C:\Windows`, which is fine — System32's copy loads). `run_edi.py` dumps the bundle inventory and, on import failure, a **PE import-table lint** of the failing Qt module (`[selftest] OK <name> -> bundle|System32` / `MISSING <name>`) under `EDI_SELFTEST`. The windowed bootloader (`runw.exe`, `console=False`) swallows the fatal message into an invisible dialog; `edi.spec` therefore also builds a **console twin `Edi-selftest.exe`** (win32 branch only, shares Analysis/pyz, ~+30s pack) that `build-windows.ps1` smoke-tests instead: `Start-Process -RedirectStandardOutput/-RedirectStandardError` captures the real `Error extracting <entry>: <errno>` line and dumps it into the job log (still also parses `EDI_SELFTEST_OUT`). The twin is deleted before the artifact phase so the `dist-app/Edi-*.exe` glob ships only `Edi.exe` + the NSIS setup.
- `pyproject.toml` sets `pythonpath=["."]`, so run pytest from the repo root; running it elsewhere breaks `import backend`.
- QtWebEngine segfaults at interpreter exit in headless/container pytest runs (tests pass, job fails with exit 139). `tests/conftest.py` `pytest_sessionfinish` registers an `atexit` `os._exit` that passes pytest's real exit status and skips Qt teardown. Keep the handler registered only at session end, not at import, so real crashes mid-run still propagate as signals.
- The onefile binary self-extracts ~450 MB to `$TMPDIR` on every launch. `/tmp` is often a small tmpfs, so the smoke tests (`build-pyzip.sh`, CI `build` job) point `TMPDIR` at a disk-backed `build/tmp`. A full write there surfaces as `Failed to extract ...: decompression resulted in return code -1` — that return code is the bootloader's `Z_ERRNO`, set only when `fwrite` fails while unpacking (a corrupt archive would show -2/-3/-4), so it means temp space ran out, not a broken binary. The selftest `os._exit`s without Qt teardown, so a QtWebEngine subprocess can outlive the parent and re-launch the onefile bootloader; `build-pyzip.sh` therefore waits for `dist-app/edi` processes to exit before removing the smoke temp dir, or a late one fails with `Could not create temporary directory!`.

## Distribution (hard-won constraints — do not break)

- The shipped binary MUST be built on **Ubuntu 22.04 (glibc 2.35)** so it runs on older desktop Linux. `scripts/build-pyzip.sh` pins everything inside Docker for this; host-built binaries are not portable and must not be shipped.
- **`libstdc++.so.6` and `libgbm.so.1` must never be bundled** (`edi.spec` `GL_HOST_DEPS` filters them out). Bundling the 22.04 copies breaks host Mesa/LLVM loading: libstdc++ crashes with `GLIBCXX_3.4.32 not found`, and libgbm (Mesa's buffer manager) makes QtWebEngine's GPU process print `did not find extension DRI_Mesa version 1` / `EGL: Failed to initialize GBM device` and fall back to software rendering on any host whose Mesa is newer than 22.04's.
- **Qt bundle pruning in `edi.spec`**: Edi uses only the QtWebEngine *widgets* API, so `excludes=['PySide6.QtQml', 'PySide6.QtQuick']` keeps hook-PySide6.QtQml from firing — otherwise it drags in the entire `qml/` tree (~4,850 plugin files) plus every Qt lib those plugins reference (Qt3D, QtQuick3D, QtCharts, QtGraphs, QtVirtualKeyboard, ...). The libQt6Qml/libQt6Quick shared libs WebEngineCore genuinely links against are still pulled by binary dependency analysis, so this is safe. `QT_DEAD_PREFIXES` additionally drops the on-screen-virtual-keyboard input-context plugin and its libs (match the soname-form dest too — PyInstaller emits both `PySide6/Qt/lib/...` and top-level `libQt6...` entries). Verify with `rg -c 'libQt6' build/edi/PKG-00.toc` (expect ~100, not 468) and the smoke test.
- **PyInstaller archive compression**: the CArchive (PKG) step defaults to zlib **level 9**, which makes the onefile pack step dominate build time. Build with `PYINSTALLER_ZLIB_COMPRESSION_LEVEL=1` (set in `Dockerfile.pyzip` and the CI `build` job) — ~3x faster pack; the binary grows ~18 MiB but every release wrapper (.deb/.rpm/.tar.gz/.AppImage) recompresses anyway.
- The app icon (`scripts/assets/app-icon.png`) is generated from `scripts/generate-icon.mjs` and bundled via `edi.spec` `datas`. `backend/window.py` `load_app_icon()` guards `sys._MEIPASS` (built binary vs. source run) — keep that guard. The about dialog reuses the same artwork (`load_about_logo()` scales `scripts/assets/app-icon.png`); the old `assets/edi-logo.png` was deleted — do not reintroduce a separate logo. The same script now also writes `app-icon.ico` (16–256, for the Windows EXE resource/installer) and `app-icon.icns` (16–1024, for the macOS BUNDLE); both are gitignored build artifacts regenerated before each native pyinstaller run.
- **Windows/macOS binaries**: PyInstaller cannot cross-compile, so each OS must build on that OS. `edi.spec` branches on `sys.platform` over a shared `Analysis` (datas + QtQml/QtQuick excludes are platform-independent): only the Linux branch applies `GL_HOST_DEPS` / `QT_DEAD_PREFIXES` and keeps the lowercase `edi` EXE name; the `win32` branch names the EXE `Edi`, attaches `scripts/assets/app-icon.ico` and a `VSVersionInfo` (version parsed from `backend/__init__.py` at spec time so it cannot drift from the tag); the `darwin` branch makes `Edi` + a `BUNDLE` into `Edi.app` with an Info.plist declaring the icon and `bundle_identifier=com.mrdanpsmith.edi`.
- **Windows CI**: the `build-windows` job runs on the GitLab-hosted `saas-windows-medium-amd64` runner (PowerShell shell, elevated; preinstalled Python ≥ 3.10, Chocolatey fallback), v* tags only, alongside the Linux `build` job. It needs **no Node/npm**: the frontend `dist/` and `scripts/assets/app-icon.ico` come byte-identical from the `frontend` CI job's artifacts (see DAG below), so the runner's preinstalled Node 21 is irrelevant. `scripts/build-windows.ps1` pins the same runtimes as Linux — `PySide6==6.11.1`, `pyinstaller==6.22.0` — into a checkout-local `.venv-win`, builds the onefile, smoke-tests it offscreen by parsing the `EDI_SELFTEST_OUT` file (no stdout on a windowed build), renames it to `Edi-<ver>-win64.exe`, and wraps it with NSIS into `Edi-<ver>-win64-setup.exe` (`packaging/edi.nsi`: admin install to `$PROGRAMFILES64\Edi`, Start Menu/Desktop shortcuts, Add/Remove entry). The `release` job pulls the `.exe` artifacts through its `needs` edge (explicit `needs` — build-windows — limits artifact downloads to exactly what each job consumes).
- **macOS is out of CI** (hosted macOS runners are Premium/Ultimate-only). `scripts/build-macos.sh` (Darwin-only; brew-installs Node 20+/Python 3.10+ as needed) mirrors the Linux steps into `dist-app/Edi.app`, ad-hoc code-signs it (`codesign --force --deep -s -`, arm64 will not launch unsigned), smoke-tests the bundle binary, then wraps it into `dist-app/Edi-<ver>-macos-arm64.dmg` (drag-to-Applications, `Applications` symlink). Apple Silicon only; unsigned/not-notarized (no Apple Developer account), so Gatekeeper warns on first open — accepted, documented tradeoff; don't add signing stubs that imply Developer-ID signing works.
- `PySide6==6.11.1` and other pins live in `requirements.txt`; keep PySide6 pinned (Qt releases break the WebEngine hooks).

## CI (`.gitlab-ci.yml`)

- Coverage reports must be **cobertura** (`coverage_format: cobertura`); GitLab rejects lcov. The `test` job collects BOTH the frontend report (`coverage/cobertura-coverage.xml`, Vitest v8) and the backend report (`coverage-py/cobertura-coverage.xml`, coverage.py `xml` output, which is Cobertura format) via the wildcard `path: '**/cobertura-coverage.xml'` — GitLab merges wildcard matches into one set of MR diff annotations. The two paths must stay consistent with that glob. (pytest-cov 7 has no `cobertura` reporter; use `xml:...`, it emits Cobertura.)
- QtWebEngine hangs in containers with small `/dev/shm` / no GPU: set `QTWEBENGINE_CHROMIUM_FLAGS="--disable-dev-shm-usage --disable-gpu"` (and `QTWEBENGINE_DISABLE_SANDBOX=1`) for any headless Qt run.
- The `test` job must run `npm run build` before `pytest` (backend tests load `dist/index.html`).
- Compute-conscious CI setup: all jobs run in a prebuilt **builder image** (`$CI_REGISTRY_IMAGE/edi-builder:jammy`, built from `Dockerfile.ci` by the `build-image` job — only on the default branch when `Dockerfile.ci`/`requirements.txt`/`.gitlab-ci.yml` change; it does NOT run on tags, because main rebuilds the image whenever its definition changes, so a release tag always finds it). It bakes the ~30 Qt runtime libs, Node 22, and a venv at `/opt/edi/venv` (PySide6==6.11.1, pyinstaller==6.22.0, pytest, pytest-qt, pytest-cov). Jobs link it with `ln -s /opt/edi/venv .venv` (package-linux.sh hardcodes `$ROOT/.venv`) and `npm ci` where needed. **Never pip-install into the baked venv at job time** — it's a read-only layer; bake changes into the image. This replaced the old per-job apt + Node-tarball + venv anchors and killed the pip cache entirely. `build-image` must create a `docker-container` buildx driver (`docker buildx create --driver docker-container`) — the default `docker` driver errors with "Cache export is not supported for the docker driver" on `--cache-to type=registry`. The buildx build command must pass `-f Dockerfile.ci` explicitly — the repo root also has a plain `Dockerfile` (the app's container image: node frontend stage + `ubuntu:26.04` runtime), which buildx builds by default and which would produce a node-less image with the venv at `/app/.venv` instead of `/opt/edi/venv`. No `when: manual` on build-image: a paused manual job blocks its `needs` dependents in the DAG. Known limitation: fork/MR pipelines pull the image from the fork's (empty) registry and fail — acceptable for a personal project.
- The `cache:` stores only `$CI_PROJECT_DIR/.npm` via `NPM_CONFIG_CACHE` (keyed on `package-lock.json`) — never `node_modules/` or `.venv/`, which together exceed the ~1 GB shared-runner cache cap and caused cache misses + full re-installs every run. `npm ci` deletes node_modules anyway, so the warm npm cache is what makes it fast. CI deps live only in the runner/builder image, not on the host.
- The `test` job is the single quality gate: `npm run lint` + `npm run typecheck` + `npm run coverage` (Vitest unit tests) + `npm run build` + `.venv/bin/pytest`. There is no separate `check` job (a separate job meant an extra `npm ci`/image pull and put `check` on the tag critical path; the frontend check runs only once, in the `frontend` job). Keep local `npm run check` as the full gate. The tag-only `frontend` job is NOT a check job to be avoided — it is the single producer of the platform-independent `dist/` + `.ico/.icns` that both `build` and `build-windows` consume, so the platform builds never recompile the frontend and the Windows runner needs no Node (see DAG below).
- The `build` (PyInstaller) job is gated by `rules` to `v*` tags only — it is not run on branch/MR pipelines or the default branch (its binary artifact is consumed only by `package`/`release`, so bundling on main was wasted runner time; the tradeoff is a pyinstaller regression surfaces only on a tag).
- Tag-pipeline DAG: `build-image` (prepare, only when its definition changes) → `test` and `frontend` in parallel (both `needs: {job: build-image, optional: true}`; `frontend` does `npm ci` + `generate-icon` + `npm run lint` + `npm run build`, shipping `dist/` + icons as small artifacts) → `build` and `build-windows` in parallel (both `needs: [build-image(optional), frontend]`, no dependency on each other; `build` runs pyinstaller only — lint/typecheck already ran in the `frontend` job — keeping the release gated) → `package` (`needs: [build]`) → `release` (`needs: [package, build-windows]`). Every non-build-image job adds `needs: {job: build-image, optional: true}` so pipelines proceed when the image is already current. Keeping `needs` explicit also limits artifact downloads to exactly what each job consumes (`build-windows` pulls only the small `frontend` artifacts, never the ~193 MB onefile; `release` pulls only the four packaged files).
- `release` job publishes via `glab` on `v*` tags, authenticated by CI auto-login with the built-in `CI_JOB_TOKEN` (JOB-TOKEN header). Do NOT set `GITLAB_TOKEN=$CI_JOB_TOKEN`: glab sends it as PRIVATE-TOKEN, which the Releases API rejects with 404. Requires the project setting "Allow CI job token to create releases" enabled.
- Linux dock/taskbar icon comes from a `.desktop` file (not the window icon), so the bare binary shows a generic gear without one. `scripts/install-desktop.sh` installs `~/.local/share/icons/hicolor/512x512/apps/edi.png` + `~/.local/share/applications/edi.desktop` (template `scripts/assets/edi.desktop`, `Exec` substituted); `app.setDesktopFileName("edi")` in `backend/main.py` hints the WM to match it.
- Release artifacts are versioned and wrapped: the CI `package` job (v* tags only) runs `scripts/package-linux.sh`, which wraps the already-built onefile (never recompiles; inherits the glibc 2.35 build) into `edi_<v>_amd64.deb`, `edi-<v>-1.x86_64.rpm`, `edi-<v>-linux-x86_64.tar.gz`, `Edi-<v>-x86_64.AppImage`. The `release` job publishes all four via `glab release create --use-package-registry` (multi-file is supported) and refuses to run if `$CI_COMMIT_TAG != v$(version.sh current)`. `rpm` and `file` (required by appimagetool and rpm's brp scripts) are baked into the builder image.
- Runtime dependency lists live in `scripts/package-linux.sh`: `DEB_DEPENDS` (Debian names) and `RPM_REQUIRES` (different names — e.g. `libnss3`→`nss`, `libasound2`→`alsa-lib`, `libpulse0`→`pulseaudio-libs`, `libgssapi-krb5-2` merges into `krb5-libs`). The .deb is validated on a clean `ubuntu:22.04` container (apt resolves Depends and `EDI_SELFTEST=1` runs); the .rpm needs a Fedora/Rocky box for the full dnf resolution test (this sandbox cannot reach `mirrors.fedoraproject.org`). `%global _debug_package 0` in `packaging/edi.spec.in` stops rpmbuild's find-debuginfo from choking on the prebuilt binary; `rpmbuild` needs `--define "_dbpath <dir>"` when building as non-root.
- `dpkg-deb` output is forced to `-Zxz` (`packaging/control.in`) so old apt can read it; the hicolor icon set (16–512) is scaled from the 1024 source with a PySide6 `QImage` snippet (headless, no QApplication needed). AppImage uses `appimagetool` pinned to `1.9.1` (fallback: `continuous`), run with `APPIMAGE_EXTRACT_AND_RUN=1` (no FUSE in CI) from the stage dir so the output lands there. The AppImage's squashfs zstd level is lowered to 1 via `--mksquashfs-opt -Xcompression-level 1` — mksquashfs's default level 15 is slow on the ~180 MB payload for a few percent less size.
