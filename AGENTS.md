# AGENTS.md

Edi is a markdown editor. Frontend: ProseMirror (the document editor) + CodeMirror 6 (embedded code blocks only) + Mermaid + spreadsheet formulas (TypeScript/Vite) compiled to a static `dist/`. Backend: Python 3 + PySide6/QtWebEngine. A native `QWebEngineView` hosts `dist/index.html`; the page talks to Python via `QWebChannel` (`backend/bridge.py`). This is NOT a plain web app — `npm run dev` runs only the Vite server; the real app is Python.

## Find / replace

`src/search.ts` is a ProseMirror plugin + pure matching layer; `src/searchPanel.ts` is the `#edi-search-bar` UI. Search runs over the document's raw flat text — every text node (including fenced code blocks) plus the `attrs.value` markup of `table`/`mermaid_block` atoms — and highlights matches on the rendered editor via inline decorations (with whole-block `NodeSelection` for atom matches). Masked fields, images and source blocks contribute no searchable text. Replace preserves marks; a table's pipe value refuses a replacement containing `\n` (row corruption). The document focus follows the search: typing or toggling a flag jumps the caret/scroll to the first match while the panel keeps keyboard focus (plain doc edits do NOT reset the active match — `SearchPanel.refresh()` re-applies only after a doc swap), Enter/Shift+Enter step matches, and spreadsheet/plain view tables additionally scroll the cell under the match into view (`onSearchChange`/`scrollActiveCellIntoView` in `src/node/table.ts`). Esc closes, Ctrl+F opens find and Ctrl+H the find+replace bar (wired in `src/main.ts`, `src/menus.ts`, `backend/window.py`'s Edit menu).

## Spreadsheet formulas

`src/formulas.ts` is the single source of truth for the function registry and value/coercion helpers; `src/spreadsheet.ts` is the parser/evaluator and evaluates through a `FormulaEnv` (`{ functions: ReadonlyMap<string, FormulaFunction> }`, looked up case-insensitively). `solve`, `computeSpreadsheet`, `resolveTableValue`, `proseToMarkdown`, and `serializeDocToHtml` all take an optional env that defaults to `BUILTIN_ENV`, so any path that re-serializes a resolved table must thread the document's env through (the editor's `getMarkdown`, export, and the table node view all do). `series.ts` derives `FORMULA_FUNCTIONS` from `BUILTIN_FUNCTION_NAMES`, and `formulaReference.ts` generates the Help → Formula Reference document from `BUILTIN_FORMULAS`, so a new builtin cannot drift between the evaluator, reference-shifting, and docs.

Document-local functions come from `code_block` nodes with `language === 'edi-formula'`, one `NAME(params) = expression` per line (`#` starts a comment). `src/formulaDsl.ts` parses/compiles them, rejecting builtin-name collisions, duplicate names, and cycles; `src/formulaDefs.ts` is an editor plugin that compiles every such block (document-wide) into a `FormulaEnv` in plugin state, decorates rejected blocks with `.edi-formula-invalid`, and exposes it via `formulaEnvFor(state)` / `documentFunctionsFor(state)`. Builtins are never overridable, and a rejected definition makes cells that call it resolve the usual `#NAME?` error. Function-name autocomplete lives in `src/formulaAutocomplete.ts`, fed by the table node view's `formulaFunctions()` (builtins + document defs).

- `npm run audit` — `npm audit --audit-level=high` (needs network). Currently clean (0 vulnerabilities); the vitest toolchain is pinned to the patched 4.1.11 line, so do not let it drift back below that.
- Python static analysis, both in the CI `test` job and locally:
  - `.venv/bin/bandit -c pyproject.toml -r backend scripts/color-scheme-probe.py scripts/dark-mode-forensics.py run_edi.py -q` — source-security scan; gates on **every** finding at any severity. `[tool.bandit] skips = ["B404"]` in `pyproject.toml` suppresses the pure "consider importing subprocess" advisory (the real call sites stay gated by B603/B607); the deliberate uses — allow-listed code-block exec (`exec.py`), `gsettings get` and `xdg-open` (both resolved via `shutil.which` to absolute paths) — are documented with bare `# nosec B603` on the call line and a rationale comment just above (never put extra words after the test ID or bandit warns on every token).
  - `.venv/bin/pip-audit -r requirements.txt` — OSV dependency audit (needs network); audits the app's declared deps, NOT the venv's own `pip` (the venv's stale pip 25.x has CVEs that would otherwise be false alarms).
- `.venv/bin/pytest tests/` — backend tests. **Requires `dist/` to exist first** (run `npm run build`); `tests/test_window.py` fails fast with a clear message otherwise. Also reports coverage (pytest-cov, from `pyproject.toml` `addopts`): term-missing table on stdout + Cobertura XML at `coverage-py/cobertura-coverage.xml` (needs pytest-cov installed; it's in `requirements.txt`).
- `./scripts/install-deps.sh` — one-time setup: `.venv/` (PySide6 + pytest + pytest-cov + bandit + pip-audit) + `npm install` + generates `scripts/assets/app-icon.png` via `node scripts/generate-icon.mjs`.
- `./scripts/simulate-ci-test.sh [--pytest-only] [--rebuild-image]` — **local simulation of the CI `test` job**. Runs the exact job steps inside the `edi-builder:jammy` image (built from `Dockerfile.ci` on demand): Python **3.10** `compileall` over backend/tests/scripts, `npm ci`, lint, typecheck, dupcheck, frontend coverage, `npm run build`, bandit, `/opt/edi/venv/bin/pytest tests/`, then the network audits (`npm audit`, `pip-audit`). Use it before pushing to save CI minutes — the two CI-burners it catches (3.10 f-string/`compileall` syntax gates; tests depending on `gsettings`/dconf/GNOME env that the container lacks) both masqueraded as green on a host 3.14 venv. A stale local image (built before a tool like bandit/pip-audit was baked into `/opt/edi/venv`) otherwise fails mid-run with a cryptic "No such file or directory"; the script preflights the baked venv for exactly the tools its steps reference and rebuilds on demand (the Docker layer cache keeps that a no-op when `Dockerfile.ci` is current).
- `./scripts/build-pyzip.sh` — builds `dist-app/edi` (single-file binary) inside an Ubuntu 22.04 Docker container, smoke-tested offscreen.
- `./scripts/build-windows-wine.sh [VERSION]` — builds `dist-app/Edi-<ver>-win64.exe` (Windows onefile) on Linux via WineHQ inside `edi-wine-builder:jammy` (Dockerfile.wine): runs a real Windows Python 3.12 + PyInstaller under Wine so edi.spec's `win32` branch executes, then validates the build STRUCTURALLY (see the testing-quirks bullet): stages Wine's bundled ICU next to `Qt6Core.dll` so the Qt hooks collect plugins, checks the onefile CArchive actually contains the plugins + ICU (`CArchiveReader`), and bounded-smoke-tests the console twin (`SELFTEST {...}` = full pass; Wine's proven Chromium-init crash = `SELFTEST_SKIPPED_ENVIRONMENTAL`; extraction/DLL defects = hard fail), then builds the NSIS installer (`Edi-<v>-win64-setup.exe`) with the image's native Linux `makensis` (absolute `-D` defines — see the smoke bullet). Locally it `docker run`s the image with the checkout mounted at `/builds/edi` as your uid; inside a baked `edi-wine-builder` image (CI) it runs directly, re-execing as an unprivileged `ediwin` when root. Requires `dist/index.html` + `scripts/assets/app-icon.ico` (build them first, or pull the `frontend` job artifacts).

## Testing quirks

- Qt must run offscreen headlessly: `QT_QPA_PLATFORM=offscreen` + `QTWEBENGINE_DISABLE_SANDBOX=1`. `tests/conftest.py` sets these via `os.environ.setdefault` *before* importing PySide6 — never import PySide6 before the env is set.
- QtWebEngine `runJavaScript` does **not** await Promises. The packaged-binary smoke test (`EDI_SELFTEST=1`, offscreen) probes sync JS snapshots (`window.__selftest`) and, once the page finishes loading, prints one `SELFTEST {...}` line and exits 0. The app boots a **home screen** (`#app[data-view='home']`) instead of a welcome tab, so the smoke loads the page with `?selftest=1` (backend sets the query when `EDI_SELFTEST=1`); `src/main.ts` checks that flag and opens the Welcome doc so `__selftest.title` still reads `Untitled — Edi`. A 25s watchdog prints `SELFTEST_TIMEOUT` and exits 1. It uses `os._exit` to skip Qt teardown (a wedged renderer can otherwise hang the process and swallow output) and must not depend on async values or the bridge being ready. When `EDI_SELFTEST_OUT` names a file, the same verdict line is also written there before exit — required for the windowed Windows build, which has no attached console (`console=False` makes Python's sys.stdout None); both the Wine build (`scripts/build-windows-wine.sh`, bash) and the desktop `scripts/build-windows.ps1` parse that file instead of stdout. `_run_selftest` first writes a `SELFTEST_BOOTING` heartbeat to that file so a hung smoke can distinguish "still self-extracting / Qt still starting" (no heartbeat) from "Python booted but QtWebEngine never loaded" (stuck on BOOTING). `build-windows-wine.sh` polls the file rather than using a fixed wait — succeeding the moment a `SELFTEST {...}` verdict appears, but under Wine the smoke is fundamentally structural: it stops early (and classifies `SELFTEST_SKIPPED_ENVIRONMENTAL`) the moment the proven Chromium-init crash markers land in the boot log instead of grinding the **20 min budget** (`EDI_SMOKE_BUDGET_MIN` overrides), and hard-fails only on extraction/DLL-load/anomaly evidence. `build-windows.ps1` does the same on a real Windows desktop with a **3 min budget** (same `EDI_SMOKE_BUDGET_MIN` override). Run 2 hung; runs 3+ exit with code `-1`, which is the windowed bootloader relaying the **child Python process's** nonzero exit — NOT a bootloader/corrupt-archive abort, and `%TEMP%\_MEI*` was a complete extraction all along (the old "partial extract: 62 files" DIAG counted only top-level entries). When the console twin shows Python booting, the actual packaged-binary failure mode is a DLL load error (e.g. `ImportError: DLL load failed while importing QtWebEngineCore: The specified module could not be found.`). Cause (proven on GitLab's former `saas-windows-medium-amd64` runner, since replaced by the Wine build): all 20 Qt6 DLLs — every WebEngineCore companion AND Qt6WebEngineCore.dll itself — are present in the bundle; the load still fails because **Qt6WebEngineCore.dll has hard static imports of `dcomp.dll` (DWM compositor) and `bthprops.cpl` (Bluetooth shell) that Server-SKU runners do not have** (proven by parsing the win_amd64 wheel's import table with `pefile`, and by PyInstaller warning on exactly those two — everything else, incl. `msvcp140.dll`, resolves from System32). Linux pulls only the Qt libs via ELF `DT_NEEDED` so it works; and `dcomp.dll`/`bthprops.cpl` exist on normal Windows 10/11 desktops. That was necessary but NOT sufficient: the exes built by that runner (and by early Wine builds here) also shipped with **zero Qt plugins** because **Wine lacks System32's `icuuc.dll`/`icuin.dll`**, which `Qt6Core.dll` hard-imports (20 `ucnv_*` symbols, proven via `pefile` and a wine loader trace `err:module:import_dll Library icuuc.dll ... not found`). PyInstaller 6.22's Qt hooks discover the Qt install by importing `PySide6.QtCore` in an isolated subprocess; with ICU unresolvable that probe failed, the hooks found no plugins, and the onefile booted with "no Qt platform plugin could be initialized" on any real desktop. Nobody ships the DLL: the win_amd64 wheels carry only `resources/icudtl.dat`, official Qt 6.11.1 bin has no ICU DLL, and `icuuc.dll` is a Windows system DLL (present in every real System32 ≥ 1703; Wine bundles it only since the **11.5 development line** — so `Dockerfile.wine` installs **winehq-staging**, never wine-stable 11.0). The fix (2026-09): the build copies Wine's bundled ICU (`/opt/wine-*/lib/wine/x86_64-windows/icu*.dll`) into the prefix's `site-packages/PySide6/` so the hook probe succeeds and the plugins get collected canonically; `edi.spec`'s win32 branch then force-appends those ICU DLLs to the bundle (deduped, like the WebEngine companions) so the exe is self-contained even on no-ICU Windows. Both `build-windows-wine.sh` and `build-windows.ps1` therefore probe/make the venv's QtWebEngineCore import work **before** the frozen smoke (probe fail ⇒ `SELFTEST_SKIPPED_ENVIRONMENTAL`, exit 0, packaging proceeds; the `.ps1` desktop path stages System32's ICU into the venv the same way and still runs the FULL render smoke on real Windows). Under Wine specifically, the frozen onefile boots — extraction + Python + Qt init are proven — but QtWebEngine's Chromium then FATALs during init (`network_change_notifier_win.cc`: `WSALookupServiceBegin failed with: 8`; `hwnd_util.cc:65]: 1400`) and Wine parks an invisible `winedbg` dialog, so the script bounds the smoke, stops early when those markers land, kills the process tree, and classifies the crash `SELFTEST_SKIPPED_ENVIRONMENTAL` — while still hard-failing on extraction errors / `DLL load failed` / missing plugins (the CArchive structural check, 4a, is the load-bearing regression gate for the pluginless-bundle bug). The probe must run under `$ErrorActionPreference='Continue'` with `2>&1` capture and then restore EAP — Windows PowerShell 5.1 promotes native-command stderr to a terminating `NativeCommandError` when EAP is 'Stop' (that aborted the job before the skip logic ran on the first attempt). `edi.spec`'s win32 branch still explicitly appends the WebEngine companion set (`Qt6WebEngineCore/Qt6WebEngineWidgets/Qt6Qml/Qt6Quick/Qt6QuickWidgets/Qt6QmlModels/Qt6QmlWorkerscript/Qt6Positioning/Qt6WebChannel/Qt6Network/Qt6PrintSupport`) to `a.binaries` as `(dest, src, 'BINARY')`, deduped against `b[0]` dests already collected. Note the bundle root holds NO Qt DLLs — they extract to the `PySide6/` subdirectory (System + python DLLs sit at the root; the msvcp140 family is never collected because PyInstaller excludes everything resolved under `C:\Windows`, which is fine — System32's copy loads). `run_edi.py` dumps the bundle inventory and, on import failure, a **PE import-table lint** of the failing Qt module (`[selftest] OK <name> -> bundle|System32` / `MISSING <name>`) under `EDI_SELFTEST`. The windowed bootloader (`runw.exe`, `console=False`) swallows the fatal message into an invisible dialog; `edi.spec` therefore also builds a **console twin `Edi-selftest.exe`** (win32 branch only, shares Analysis/pyz, ~+30s pack) that `build-windows.ps1` smoke-tests instead: `Start-Process -RedirectStandardOutput/-RedirectStandardError` captures the real `Error extracting <entry>: <errno>` line and dumps it into the job log (still also parses `EDI_SELFTEST_OUT`). The twin is deleted before the artifact phase so the `dist-app/Edi-*.exe` glob ships the versioned onefile **and** the installer (`Edi-<v>-win64-setup.exe`) — the NSIS installer is now ALSO built by the wine job (native Linux makensis, `nsis` baked into the image; no Wine needed). The Path-quirks lesson from the old runner still applies: makensis resolves relative `File`/`OutFile` paths against the **script's** directory, not the CWD, so `build-windows-wine.sh` passes `-DSETUPEXE`/`-DICO`/`-DOUTEXE` as **absolute** paths (Linux makensis also takes `-D`, not `/D`); `edi.nsi` exposes an optional `OUTEXE` define so the output lands in the checkout root, not `packaging/`. `build-windows.ps1` can still build one on a real Windows desktop (`packaging/edi.nsi` stays desktop-compatible).
- `pyproject.toml` sets `pythonpath=["."]`, so run pytest from the repo root; running it elsewhere breaks `import backend`.
- QtWebEngine segfaults at interpreter exit in headless/container pytest runs (tests pass, job fails with exit 139). `tests/conftest.py` `pytest_sessionfinish` registers an `atexit` `os._exit` that passes pytest's real exit status and skips Qt teardown. Keep the handler registered only at session end, not at import, so real crashes mid-run still propagate as signals.
- The onefile binary self-extracts ~450 MB to `$TMPDIR` on every launch. `/tmp` is often a small tmpfs, so the smoke tests (`build-pyzip.sh`, CI `build` job) point `TMPDIR` at a disk-backed `build/tmp`. A full write there surfaces as `Failed to extract ...: decompression resulted in return code -1` — that return code is the bootloader's `Z_ERRNO`, set only when `fwrite` fails while unpacking (a corrupt archive would show -2/-3/-4), so it means temp space ran out, not a broken binary. The selftest `os._exit`s without Qt teardown, so a QtWebEngine subprocess can outlive the parent and re-launch the onefile bootloader; `build-pyzip.sh` therefore waits for `dist-app/edi` processes to exit before removing the smoke temp dir, or a late one fails with `Could not create temporary directory!`.

## Distribution (hard-won constraints — do not break)

- The shipped binary MUST be built on **Ubuntu 22.04 (glibc 2.35)** so it runs on older desktop Linux. `scripts/build-pyzip.sh` pins everything inside Docker for this; host-built binaries are not portable and must not be shipped.
- **`libstdc++.so.6` and `libgbm.so.1` must never be bundled** (`edi.spec` `GL_HOST_DEPS` filters them out). Bundling the 22.04 copies breaks host Mesa/LLVM loading: libstdc++ crashes with `GLIBCXX_3.4.32 not found`, and libgbm (Mesa's buffer manager) makes QtWebEngine's GPU process print `did not find extension DRI_Mesa version 1` / `EGL: Failed to initialize GBM device` and fall back to software rendering on any host whose Mesa is newer than 22.04's.
- **Qt bundle pruning in `edi.spec`**: Edi uses only the QtWebEngine *widgets* API, so `excludes=['PySide6.QtQml', 'PySide6.QtQuick']` keeps hook-PySide6.QtQml from firing — otherwise it drags in the entire `qml/` tree (~4,850 plugin files) plus every Qt lib those plugins reference (Qt3D, QtQuick3D, QtCharts, QtGraphs, QtVirtualKeyboard, ...). The libQt6Qml/libQt6Quick shared libs WebEngineCore genuinely links against are still pulled by binary dependency analysis, so this is safe. `QT_DEAD_PREFIXES` additionally drops the on-screen-virtual-keyboard input-context plugin and its libs (match the soname-form dest too — PyInstaller emits both `PySide6/Qt/lib/...` and top-level `libQt6...` entries). Verify with `rg -c 'libQt6' build/edi/PKG-00.toc` (expect ~100, not 468) and the smoke test.
- **PyInstaller archive compression**: the CArchive (PKG) step defaults to zlib **level 9**, which makes the onefile pack step dominate build time. Build with `PYINSTALLER_ZLIB_COMPRESSION_LEVEL=1` (set in `Dockerfile.pyzip` and the CI `build-linux` job) — ~3x faster pack; the binary grows ~18 MiB but every release wrapper (.deb/.rpm/.tar.gz/.AppImage) recompresses anyway.
- **Frontend must be a single JS bundle — no runtime `import()`**: the app ships to QtWebEngine as `dist/index.html` under `file://`, and QtWebEngine intermittently fails runtime dynamic module fetches under load (`Uncaught (in promise) TypeError: Failed to fetch dynamically imported module`). That was the root cause of the chronically flaky `tests/test_mermaid_templates.py` (mermaid's internal `mermaid.core.js` split chunk failing) and can hit real users as "Mermaid render error". `vite.config.ts` therefore sets `build.rolldownOptions.output.codeSplitting: false` — one ~5.4 MB minified bundle, no async chunks (the remaining `import(` in the minified output is ESLint-mode regex text / an `import.meta.resolve` feature-detect). Do NOT re-enable code-splitting for "perf" — the depot is local disk; the lazy-loading it buys has cost intermittent renderer errors.
- The app icon (`scripts/assets/app-icon.png`) is generated from `scripts/generate-icon.mjs` and bundled via `edi.spec` `datas`. `backend/window.py` `load_app_icon()` guards `sys._MEIPASS` (built binary vs. source run) — keep that guard. The about dialog reuses the same artwork (`load_about_logo()` scales `scripts/assets/app-icon.png`); the old `assets/edi-logo.png` was deleted — do not reintroduce a separate logo. The same script now also writes `app-icon.ico` (16–256, for the Windows EXE resource/installer) and `app-icon.icns` (16–1024, for the macOS BUNDLE); both are gitignored build artifacts regenerated before each native pyinstaller run.
- **Windows/macOS binaries**: PyInstaller cannot cross-compile, so each OS's bundle is produced on a machine that provides that OS's runtime. Windows is now built on Linux via a WineHQ container (see the Wine build bullet); macOS still MUST build on macOS. `edi.spec` branches on `sys.platform` over a shared `Analysis` (datas + QtQml/QtQuick excludes are platform-independent): only the Linux branch applies `GL_HOST_DEPS` / `QT_DEAD_PREFIXES` and keeps the lowercase `edi` EXE name; the `win32` branch names the EXE `Edi`, attaches `scripts/assets/app-icon.ico` and a `VSVersionInfo` (version parsed from `backend/__init__.py` at spec time so it cannot drift from the tag); the `darwin` branch makes `Edi` + a `BUNDLE` into `Edi.app` with an Info.plist declaring the icon and `bundle_identifier=com.mrdanpsmith.edi`.
- **Windows CI**: the `build-windows` job builds the `.exe` on ordinary Linux runners inside the `ghcr.io/<owner>/edi-wine-builder:jammy` image (built+pushed by `images.yml` from `Dockerfile.wine`, on tag-run/manual-validation v* runs, alongside the Linux `build-linux` job). `Dockerfile.wine` is Ubuntu 22.04 + WineHQ **`winehq-staging`** (i386 arch enabled; staging tracks the ≥11.5 devline whose Wine bundles the system ICU that `Qt6Core.dll` needs — wine-stable 11.0 is too old) with the **win_amd64 wheels baked in** (`/opt/wheels`, downloaded at image-build time — no Wine TLS) and the**Windows Python installer** (`/opt/py`, pin 3.12.8, shared via `requirements-win.txt` = `PySide6==6.11.1` + `pyinstaller==6.22.0` + `pefile` + `pywin32-ctypes` + `defusedxml`, `REQ_HASH` build-arg invalidates the wheel bake when the pins change; `EDI_WINE_REFRESH` does the same for the unpinned winehq apt layer). pefile/pywin32-ctypes are PyInstaller's `sys_platform == "win32"` deps; `pip download --platform win_amd64` on Linux evaluates markers against the *host*, so they must be pinned explicitly or the offline install fails. No prefix is baked: `scripts/build-windows-wine.sh` creates `build/wine-prefix` at job time (pin-stamped; reruns reuse it). The Python installer is a **GUI bootstrapper** and is killed instantly headless (wine reports 128+SIGINT), so prefix init + the installer run under `xvfb-run`; pip/PyInstaller are console apps and stay headless. CI container jobs run as root and **Wine refuses to run as root**, so the script re-execs itself as an unprivileged `ediwin` user (chowning just `build/` + `dist-app/`). The same script is the **local** iteration path: it `docker run`s the image with the checkout mounted at `/builds/edi` as the host uid. The frontend `dist/` + `app-icon.ico` come byte-identical from the `frontend` job's artifacts, so the job needs no Node/npm. Validation is STRUCTURAL (see the smoke bullet) — a full render only happens by running `scripts/build-windows.ps1` on a real Windows desktop (it remains the desktop path: `.venv-win` for `PySide6==6.11.1`/`pyinstaller==6.22.0`, offscreen smoke via `EDI_SELFTEST_OUT`, renamed to `Edi-<ver>-win64.exe`). The NSIS installer (`Edi-<v>-win64-setup.exe`) is now built by the same wine job (native Linux makensis; see the smoke/ICU bullet for the path-quirk rules). The `release` job pulls the `.exe` through its `needs` edge (explicit `needs` — build-windows — limits artifact downloads to exactly what each job consumes).
- **macOS CI runs on GitHub Actions' free arm64 `macos-15` runners** (the `build-macos` job, gated to `v*` tags / manual validation like the other binary jobs). `scripts/build-macos.sh` (Darwin-only; brew-installs Node 20+/Python 3.10+ as needed) mirrors the Linux steps into `dist-app/Edi.app`, ad-hoc code-signs it (`codesign --force --deep -s -`, arm64 will not launch unsigned), smoke-tests the bundle binary, then wraps it into `dist-app/Edi-<ver>-macos-arm64.dmg` (drag-to-Applications, `Applications` symlink). Apple Silicon only; unsigned/not-notarized (no Apple Developer account), so Gatekeeper warns on first open — accepted, documented tradeoff; don't add signing stubs that imply Developer-ID signing works.
- `PySide6==6.11.1` and other pins live in `requirements.txt`; the Windows build mirrors them (`PySide6==6.11.1` + `pyinstaller==6.22.0` + `defusedxml` in `requirements-win.txt`, consumed by Dockerfile.wine and `scripts/build-windows.ps1`); keep PySide6 pinned (Qt releases break the WebEngine hooks).
- `backend/tables.py` (Insert → Spreadsheet) parses ODS/XLSX XML with **`defusedxml`** as a drop-in for `xml.etree.ElementTree` — plain ElementTree is XML-bomb vulnerable on user-opened files, and bandit greets it with a Medium finding. It is a runtime import, so every PyInstaller build venv must install it, not just the dev/CI venv: `Dockerfile.pyzip`, `Dockerfile.wine`, `scripts/build-windows.ps1` and `scripts/build-macos.sh` each pin it explicitly alongside PySide6 (PyInstaller collects it automatically once it's importable).

## CI (GitHub Actions — `.github/workflows/ci.yml` + `release.yml` + `images.yml`)

- Two workflows, two pipelines: **`ci.yml` (name `CI`)** is the normal commit pipeline — runs on every push to `main` / `release/**` branches and only runs the testing phases (`frontend` + `test`), never binaries or releases. **`release.yml` (name `Release`)** is the full tag-gated DAG (`v*` tags or manual `workflow_dispatch`, `VER` defaulting to `0.0.0`) — the same quality gate plus the platform builds, packaging, and publishing. The `frontend`/`test` job bodies are **deliberately mirrored** across both files (each pipeline stays self-contained); that's why `.jscpd.json` ignores `**/.github/workflows/**`.

- Coverage stays **cobertura**: `npm run coverage` → `coverage/cobertura-coverage.xml` (Vitest v8), pytest → `coverage-py/cobertura-coverage.xml` (pytest-cov 7 has no `cobertura` reporter; `xml:...` output is Cobertura). GitHub has no native MR diff annotations, so the `test` job posts a job-summary tail of both tables instead (a Codecov bolt-on can be revisited later; keep the two `coverage*/cobertura-coverage.xml` paths stable).
- QtWebEngine hangs in containers with small `/dev/shm` / no GPU: set `QTWEBENGINE_CHROMIUM_FLAGS="--disable-dev-shm-usage --disable-gpu"` (and `QTWEBENGINE_DISABLE_SANDBOX=1`) for any headless Qt run — the workflows set these globally.
- `test` needs `dist/` for pytest (backend tests load `dist/index.html`); the `frontend` job builds it and `test` downloads the artifact.
- Compute-conscious CI setup: most jobs run **inside** a prebuilt **builder image** (`ghcr.io/<owner>/edi-builder:jammy`, built from `Dockerfile.ci` by `images.yml` — on main when `Dockerfile.ci`/`requirements.txt`/`.github/workflows/images.yml` change, never on tags, and manually via `workflow_dispatch`; run it once manually after a fresh import so ghcr has the images). It bakes the ~30 Qt runtime libs, Node 22, and a venv at `/opt/edi/venv` (PySide6==6.11.1, pyinstaller==6.22.0, pytest, pytest-qt, pytest-cov, defusedxml, bandit, pip-audit). Jobs use it as a `container:` and link the venv with `ln -s /opt/edi/venv .venv` (package-linux.sh hardcodes `$ROOT/.venv`) and `npm ci` where needed. The **`build-windows`** job instead runs in a second pushed image (`ghcr.io/<owner>/edi-wine-builder:jammy` from `Dockerfile.wine`), so its ~1 GB Wine+wheel payload never pollutes the everyday pull. Both are pushed by `images.yml` (triggered on `Dockerfile.wine`/`requirements-win.txt` changes too). **Never pip-install into the baked venvs at job time** — they're read-only image layers; bake changes into the images. `images.yml` must use a `docker-container` buildx driver (the default `docker` driver errors with "Cache export is not supported for the docker driver" on `--cache-to type=registry`) and must pass `-f Dockerfile.ci` explicitly — the repo root also has a plain `Dockerfile` (the app's container image: node frontend stage + `ubuntu:26.04` runtime), which buildx builds by default and would produce a node-less image with the venv at `/app/.venv` instead of `/opt/edi/venv`. Jobs pull the ghcr images as **public packages**, so no auth and no fork-registry failure.
- npm caching: `actions/setup-node` `cache: npm` (frontend + macOS jobs) — never `node_modules/` or `.venv/` (they exceed GitHub's cache cap and caused misses; `npm ci` deletes node_modules anyway). The Linux/Windows binary jobs need no Node at all: they consume the `edi-web` artifacts (macOS is the exception — `build-macos.sh` does its own `npm ci`).
- The quality gate is split over two jobs in both pipelines: `frontend` runs lint + typecheck + dupcheck + the production build (producing `dist/` + `.ico/.icns`); `test` runs vitest coverage + bandit + pytest + the network audits (`npm run audit`, `.venv/bin/pip-audit -r requirements.txt`) last so a transient network failure doesn't burn the deterministic gate. Keep local `npm run check` as the full gate.
- Binary jobs are gated to `v*` tags (or manual `workflow_dispatch`, where `VER` falls back to `0.0.0` for validation): `build-linux` runs in the jammy container (the glibc 2.35 pin), `build-windows` in the wine container, `build-macos` natively on a free arm64 `macos-15` runner. The tradeoff stands: a pyinstaller/Wine/Mac regression surfaces only on a tag or a manual run.
- Release-pipeline DAG (`.github/workflows/release.yml`): `frontend` → `test` (dist artifact); `frontend` → `build-linux` + `build-windows` in parallel (both consume the same `edi-web` artifacts, byte-identical to what `build-macos` builds itself — the platform builds never recompile the frontend, and the Windows build needs no Node) → `package` (`needs: build-linux`) → `release` (`needs: [package, build-windows, build-macos]`). Artifact downloads are scoped by name to exactly what each job consumes (`build-windows` pulls only the small `edi-web` artifacts + the wine image, never the ~193 MB onefile; `release` pulls only the four packaged files + the .exe + the .dmg).
- `release` publishes via `gh release create <tag> file...` on `v*` tags, authenticated by the runner's built-in `GITHUB_TOKEN` (job `permissions: contents: write`). It refuses to run if `$GITHUB_REF_NAME != v$(version.sh current)`. **Do not glob `dist-app/...` in the release job**: `upload-artifact` v4 flattens wildcard uploads (paths are preserved only "after the first wildcard"; multi-path wildcard uploads root at their LCA), so artifacts unzip flat at the artifact root — the win/mac files even lose their `Edi-` prefix. The job downloads all three artifacts into `artifacts/` and `find`-enumerates them (fails loudly if none landed).
- Linux dock/taskbar icon comes from a `.desktop` file (not the window icon), so the bare binary shows a generic gear without one. `scripts/install-desktop.sh` installs `~/.local/share/icons/hicolor/512x512/apps/edi.png` + `~/.local/share/applications/edi.desktop` (template `scripts/assets/edi.desktop`, `Exec` substituted); `app.setDesktopFileName("edi")` in `backend/main.py` hints the WM to match it.
- Release artifacts are versioned and wrapped: the CI `package` job (v* tags only) runs `scripts/package-linux.sh`, which wraps the already-built onefile (never recompiles; inherits the glibc 2.35 build) into `edi_<v>_amd64.deb`, `edi-<v>-1.x86_64.rpm`, `edi-<v>-linux-x86_64.tar.gz`, `Edi-<v>-x86_64.AppImage`. The `release` job publishes everything via `gh release create <tag> file...` (multi-file is supported) and refuses to run if `$GITHUB_REF_NAME != v$(version.sh current)`. `rpm` and `file` (required by appimagetool and rpm's brp scripts) are baked into the builder image.
- Runtime dependency lists live in `scripts/package-linux.sh`: `DEB_DEPENDS` (Debian names) and `RPM_REQUIRES` (different names — e.g. `libnss3`→`nss`, `libasound2`→`alsa-lib`, `libpulse0`→`pulseaudio-libs`, `libgssapi-krb5-2` merges into `krb5-libs`). The .deb is validated on a clean `ubuntu:22.04` container (apt resolves Depends and `EDI_SELFTEST=1` runs); the .rpm needs a Fedora/Rocky box for the full dnf resolution test (this sandbox cannot reach `mirrors.fedoraproject.org`). `%global _debug_package 0` in `packaging/edi.spec.in` stops rpmbuild's find-debuginfo from choking on the prebuilt binary; `rpmbuild` needs `--define "_dbpath <dir>"` when building as non-root.
- `dpkg-deb` output is forced to `-Zxz` (`packaging/control.in`) so old apt can read it; the hicolor icon set (16–512) is scaled from the 1024 source with a PySide6 `QImage` snippet (headless, no QApplication needed). AppImage uses `appimagetool` pinned to `1.9.1` (fallback: `continuous`), run with `APPIMAGE_EXTRACT_AND_RUN=1` (no FUSE in CI) from the stage dir so the output lands there. The AppImage's squashfs zstd level is lowered to 1 via `--mksquashfs-opt -Xcompression-level 1` — mksquashfs's default level 15 is slow on the ~180 MB payload for a few percent less size.
