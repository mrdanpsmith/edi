# AGENTS.md

Edi is a markdown editor. Frontend: ProseMirror (the document editor) + CodeMirror 6 (embedded code blocks only) + Mermaid + spreadsheet formulas (TypeScript/Vite) compiled to a static `dist/`. Backend: Python 3 + PySide6/QtWebEngine. A native `QWebEngineView` hosts `dist/index.html`; the page talks to Python via `QWebChannel` (`backend/bridge.py`). This is NOT a plain web app — `npm run dev` runs only the Vite server; the real app is Python.

## Find / replace

`src/search.ts` is a ProseMirror plugin + pure matching layer; `src/searchPanel.ts` is the `#edi-search-bar` UI. Search runs over the document's raw flat text — every text node (including fenced code blocks) plus the `attrs.value` markup of `table`/`mermaid_block` atoms — and highlights matches on the rendered editor via inline decorations (with whole-block `NodeSelection` for atom matches). Masked fields, images and source blocks contribute no searchable text. Replace preserves marks; a table's pipe value refuses a replacement containing `\n` (row corruption). The document focus follows the search: typing or toggling a flag jumps the caret/scroll to the first match while the panel keeps keyboard focus (plain doc edits do NOT reset the active match — `SearchPanel.refresh()` re-applies only after a doc swap), Enter/Shift+Enter step matches, and spreadsheet/plain view tables additionally scroll the cell under the match into view (`onSearchChange`/`scrollActiveCellIntoView` in `src/node/table.ts`). Esc closes, Ctrl+F opens find and Ctrl+H the find+replace bar (wired in `src/main.ts`, `src/menus.ts`, `backend/window.py`'s Edit menu).

## Spreadsheet formulas

`src/formulas.ts` is the single source of truth for the function registry and value/coercion helpers; `src/spreadsheet.ts` is the parser/evaluator and evaluates through a `FormulaEnv` (`{ functions: ReadonlyMap<string, FormulaFunction> }`, looked up case-insensitively). `solve`, `computeSpreadsheet`, `resolveTableValue`, `proseToMarkdown`, and `serializeDocToHtml` all take an optional env that defaults to `BUILTIN_ENV`, so any path that re-serializes a resolved table must thread the document's env through (the editor's `getMarkdown`, export, and the table node view all do). `series.ts` derives `FORMULA_FUNCTIONS` from `BUILTIN_FUNCTION_NAMES`, and `formulaReference.ts` generates the Help → Formula Reference document from `BUILTIN_FORMULAS`, so a new builtin cannot drift between the evaluator, reference-shifting, and docs.

Document-local functions come from `code_block` nodes with `language === 'edi-formula'`, one `NAME(params) = expression` per line (`#` starts a comment). `src/formulaDsl.ts` parses/compiles them, rejecting builtin-name collisions, duplicate names, and cycles; `src/formulaDefs.ts` is an editor plugin that compiles every such block (document-wide) into a `FormulaEnv` in plugin state, decorates rejected blocks with `.edi-formula-invalid`, and exposes it via `formulaEnvFor(state)` / `documentFunctionsFor(state)`. Builtins are never overridable, and a rejected definition makes cells that call it resolve the usual `#NAME?` error. Function-name autocomplete lives in `src/formulaAutocomplete.ts`, fed by the table node view's `formulaFunctions()` (builtins + document defs).

## Mermaid visual editing

`src/mermaid-edit.ts` is the whole visual-editing layer: `renderDiagram()` (a thin wrapper over mermaid + `responsifySvg`/`adaptDiagramColors`/`pinSvgTextColors`/`attachMermaidToolbar`/`bakeDiagram` from `src/mermaid.ts`, so the node view no longer owns that pipeline), the source patchers, the inline label editor, the kanban drag, and the notice that keeps the last good diagram on screen when the patched source stops parsing. `src/node/mermaid.ts` keeps the node view plus the mode plumbing: the `mermaid_block` `_edit` attr, `MERMAID_EDIT_KEY` (at most one diagram in edit mode, like tables), `enterDiagramEditMode()` / `exitDiagramEditMode()` / `toggleDiagramEditMode()` (wired to the hover toolbar's Edit/Done button, a double click, and the Edit diagram / Done editing context-menu items in `src/main.ts`).

Two rules the rest of the app depends on:

- **The fenced source is the document.** A visual edit is one `setNodeMarkup` transaction (`commitSource`), so undo takes a whole edit back. `commitSource` must NOT pre-set `this.currentCode`: `update()` uses it to spot a changed value, and pre-setting it makes the view skip the re-render, leaving the old diagram on screen (there is a real-engine test pinning this).
- **View mode may bake, edit mode must not.** A diagram with light native text (sequence diagrams) is baked to a bitmap in view mode, which removes every clickable label; entering edit mode re-renders the vector and marks the labels with `.mermaid-editables`.
- **Leaving edit mode must resolve the layer.** The label input is a child of the `.mermaid` block, not of the container a render replaces, so a re-render alone leaves it floating over a diagram that is no longer editable — still swallowing its own events, and holding a source snapshot that has since moved on. `exitDiagramEditMode()` (and the diagram `enterDiagramEditMode()` drops) therefore calls `finishMermaidLabelEditing(nodeDOM, true)`, which *commits* a label edit in progress, exactly as a click elsewhere would: Done's own `mousedown` calls `preventDefault()`, so the input never blurs and nothing else will resolve it. The mode transaction is dispatched **first** on purpose — the re-render it triggers then already sees `_edit: false`, so the commit's render cannot race an edit-mode render that would re-mark the labels. A plain re-render calls the same resolver with `accept: false`: nobody asked for it, and its source may have changed underneath the editor.
- **A double click anywhere ends edit mode.** The plugin's `dblclick` handler toggles the diagram under the pointer, and otherwise finishes whichever diagram is in edit mode — the gesture that turns the mode off should not have to land back on the diagram. The click is never swallowed (word selection still happens); only ones Chrome owns are left alone: `a[href]`, `button`, `input`, `textarea`, `select`, `.cm-editor`. The listener is on the editor's **scroll container** (`view.dom.parentElement`, i.e. `#editor-container`), never on `view.dom`: the editor's own box is only as tall as its content, so a document that is one short diagram (a lone board) leaves the white space under it on the scroller, where a `view.dom` listener sees nothing — the mode stayed on and Chrome answered the click itself by selecting the nearest text on the page, the document name in the status bar. It is the scroller and not `document` (which `src/node/table.ts`'s handler can afford) so a double click in a dialog sitting on top of the editor cannot reach through it. `tests/test_window.py::test_double_click_below_a_lone_board_ends_its_edit_session` pins it with the real gesture at real coordinates, asserting the point is outside `.ProseMirror` first.

**Only mappable labels are offered.** `labelTargets()` marks a label `.mermaid-editables` only when `resolveLabelSpans()` maps it to a source range *right now* — that single filter is what keeps the promise the UI makes (a label you cannot click is either Mermaid-computed, like a treemap total, an xy-chart tick, a packet bit range, a kanban assignee, a Wardley stage or a `<<stereotype>>`, or it repeats in the source with no way to tell the copies apart). Adding a family means adding a mapper, not touching the DOM walk. A `LabelRole` of `entity` marks a label the diagram refers to elsewhere (ER entity, state, class, git branch, requirement, sankey node, wardley node, venn set, journey actor), so its rename rewrites every reference via `all: true`; `text` is prose that sits in the source once. `sourceLines`/`wholeWordSpans` are the shared source-scanning primitives — match whole words, not substrings, or `date` matches inside `order_date` and the label goes ambiguous. A label mermaid wrapped across `tspan`s reads back from `textContent` with its spaces dropped (`Lack ofTraining`), so a whitespace-squeezed match records the source's own spelling in `sourceText` and the editor edits that, not the rendering's. The same holds wherever mermaid drew the source's text inside something else — a sankey node shares its element with its computed total, a requirement row is drawn under mermaid's own idea of the key (`verifymethod: test` shows as `Verification: Test`) — so `sourceText` is the source's spelling of whatever the mapper's span covers, and the input holds exactly what a commit replaces. That is also why the editor resolves from `target.text` and not from the edited text: a row is *found* by the row mermaid drew and only its value is rewritten, so a typed value alone would leave the mapper nothing to find.

**Two gates, two costs.** `tests/test_window.py::test_every_offered_label_rename_resolves` is the cheap gate: one rename per diagram, one case per distinct patch strategy (text, tspan-wrapped, entity-all-refs, value-only row, sankey first line, implicit git branch, withheld total), ~3 s for the whole set, inside the session window. It asserts the one thing that is never acceptable — the editor closed and the source never changed — and that either mermaid drew the value or the notice said it would not. `scripts/mermaid-label-probe.py` is the exhaustive one: it walks *every* offered label of *every* template through the real gesture path, prints the offered/withheld split, and exits non-zero on any silent no-op or render failure (`--type` to narrow, `--first` for a smoke pass, report into `build/`). It needs its own WebEngine page, so it stays out of pytest — that is what the two-window constraint above is about. Run it after touching mappers, mappers' regexes, or the `GENERATED_BY_FAMILY` lists; it is the only thing that can see mermaid's real DOM shape (it found the `diagramFamily` case bug and the ER substring bug, which no jsdom test could).

Mermaid's own SVG is the DOM to patch, so read it defensively: a label may be a `text` with a `tspan` child (sequence participants are `text.actor > tspan`), which is why the wrapper check upper-cases `child.tagName`. Chromium also makes `.items > .node` natively draggable, and its drag swallows the pointer stream the kanban drag listens on — cancel `dragstart` (`-webkit-user-drag: none` in CSS covers the rest). Do NOT `preventDefault()` on `pointerdown` to fix that: it would suppress label-editor clicks.

**A kanban drag moves the real card — or the whole column — and the indicator has to be *under* it.** `armDragGroup` (in `src/mermaid-edit.ts`, via `armCardDrag` / `armColumnDrag`) lifts the elements the press landed on: the transform is *appended* to the one mermaid gave each (`base + translate(dx, dy) scale(1.04)`), so restoring the drag is putting strings back rather than recomputating positions, and `stop()` always does it. A card drag lifts the one `g.node`; a **column** drag lifts the band's `g` from `.sections` *and* every card whose centre falls in that band, so the column moves with the cards still in it and one undo takes the whole move back. A card is detected by `cardAt(pointer, cards)` (direct `closest('.items > .node')` target, falling back to a coordinate hit-test through the shared `drawnElementAt`) and only a press that hit *no* card can arm a column, so a card is never mistaken for the column it stands in; the column's own frame excludes its header label so the `⋯` and the column name stay clickable. The offset is divided by the mapping `svgMapping(svg)` reports — viewBox origin, rendered rect and a scale per axis — because a drag is measured in screen pixels while the card is moved in a viewBox mermaid has scaled to fit; without it the card runs off twice as far on any board that is not drawn at 1:1, and reading one scale for both axes would drift on a container that letterboxes the drawing. Three things have to hold together here, and each was a bug before it was a rule: the svg clips (`overflow: hidden`) and `.mermaid-preview` scrolls, so the preview gets `.kanban-dragging` to switch both to `visible` or a card travelling off the board is cut off under the pointer; SVG paints in document order, so the card is re-appended to the end of `.items` (all cards are one sibling list) to be on top, and `stop()` puts it back before its own place — the model→element mapping is the *captured* `cards` array, which re-appending does not disturb, but a fresh `cardElements()` walk would; and the drop line is an svg `<line>` *inserted before `.items`*, so it is over the column's own opaque background but under every card, the dragged one included (and before `.sections` for a column's, so it is under the frames it stands between). It cannot be a positioned overlay: a child of the preview paints above the whole drawing (`z-index: 4` did exactly that, and the line drew across the card it was previewing), and the `.mermaid` host puts it *under* the board instead. Being svg-native also means `vector-effect: non-scaling-stroke` holds it at 3px on a zoomed board and its endpoints are written in the drawing's own user units, so no scroll or zoom correction is needed; a line outside the board would have to be positioned from `container.getBoundingClientRect() + container.scrollLeft`, like the `⋯` and the `✕`. The line itself (`dropLineAt`) is drawn in the gap the release acts on, spanning the column and overhanging it by `DROP_LINE_OVERHANG` (mermaid's cards are ~15px narrower than their column, so an inset line is completely hidden by the card that is about to fill the gap); the vertical offset is `DROP_LINE_GAP`. A **column** drag is the same machinery with the slot question answered differently: `columnSlotAt` counts which gap line the pointer is over (`count` gaps strictly before the pointer against the *other* columns, so a pointer over the dragged column's own band does not shift the count) and `columnGapAt` is that gap taken from the two columns on either side of it, full height, with the dragged column itself excluded. A column boundary is a single unambiguous line, so unlike a card it needs no `DROP_LINE_GAP`/`DROP_LINE_OVERHANG` nudging — `createDropLine` takes them as 0. It is the only part of a drag that answers "which slot", since a card over a three-card column can go to the first, second or third and the column outline cannot say. It is placed on *every* move, not only when the column changes, and it hides itself off the board (a release there does nothing). An empty column has no gap, so its line is centred in the band — which a drawn slot has made a card tall. The card is never dimmed: it is lifted, not ghosted, and the hole it leaves is the record of where it came from. **A card is scaled, a column is not**, which is why `liftElements` takes the scale as an argument and `armColumnDrag` passes `1`: a card is one `g`, and `scale(DRAG_LIFT_SCALE)` about its own local origin says "this is in the air", but a column is a *frame with a padding and cards inside it* and an svg transform scales about the *element's* origin — so a scaled frame grows its border and padding and pushes its cards out through the bottom, and the ones near the edge fall out of the section entirely, which reads as a column of the wrong shape travelling somewhere other than where it was dropped. A `scale` on a column's transform is a bug. **A column is not held where a card is, because it is not one element.** The board is two sibling lists — the frames in `.sections`, the cards in `.items`, the frames *first* — so every card on the board is painted over every frame, and a lift that re-appends each element to *its own parent* (right for a card, one `g` in one list) can lift a frame over the other frames and nothing else: a column in flight was drawn with its neighbours' cards lying across it, and a column *passing over* a neighbour's cards looked like it had picked them up — which is how an empty `Done` at the end of a board came to look like it was carrying `Specified`'s card. So a column's lift is a group of its own (`kanbanDragLayer`: an svg `<g class="kanban-drag-layer">` appended as the **last** child of the svg, frame first and then the cards it carries, which is the order the board itself is drawn in) and `liftElements` takes it as its `into`, putting the whole set in the one parent — its per-element restore is unchanged, because every element's own place was captured before it moved. Nothing about how either element is *painted* changes: mermaid's kanban styles key on the element's own classes (`.section-N rect`, `.node rect`, `.kanban-label`), never on the list it is in, which is worth knowing before moving anything else between those two lists. The line stays *under* the held column, the way a card's does, and `stop()` removes the group whether the drag started or not. The restore runs **backwards** for the same reason: each element goes back before the `follower` it was captured with, and with the set in a group that follower is often another lifted element still standing in the group — restoring in capture order throws `NotFoundError` on the first card, which aborts the rest of the restore *and* `hooks.drop`, so the drop is silently lost and the rest of the column stays in the group. A held card is also `pointer-events: none` (so the drop is read off the pointer, not off whatever it passes over), which makes the group invisible to a hit test — `elementFromPoint` therefore cannot answer "what is painted over the held column" without the helper lifting that for the sample (`fronted`), which is why that probe restores it rather than leaving it. The cursor says the same thing without a drag: an open hand over a card or a column, a closed one while it is in the air (`DRAG_CONTAINER_CLASS` goes on the *preview*, so the dragging rule is `.mermaid-preview.kanban-dragging …`), and a text caret over a slot — the grab rules exclude the two slot classes rather than out-specifying the caret, because a slot is nowhere and so is not held by anything. The `⋯` and the `✕` *are* positioned siblings of the svg, so they do paint over the line where the two meet — the real-engine probe therefore samples the line along its run (`overLine`) rather than trusting one point, and `elementFromPoint` is the check throughout, since a screenshot of a just-mutated DOM under the offscreen platform is a stale frame and will lie.

**A board is authored from the board, and its chrome is quiet until the pointer asks.** `attachKanbanChrome` (in `src/mermaid-edit.ts`) builds the whole layer in one pass: per real column a `mermaid-kanban-menu` `⋯` (`<column> column actions`) and per real card a `mermaid-kanban-card-remove` `✕` (`Delete the card <title>`). All share `KANBAN_BUTTON_CLASS` (`mermaid-kanban-btn`), and the open menu list and every composer are inside `KANBAN_CHROME_CLASS` — the classes `src/node/mermaid.ts` `stopEvent` and the `dblclick` handler recognise as chrome, so a press or a double click on any of them is the control's own and never reaches the diagram under it. **Adding is not in this list at all**: the board is *drawn* with somewhere to add, so the places to add are part of the diagram (below) rather than controls laid over it, and `attachKanbanChrome` has nothing to say about them — which is also why the layer's `place()` is the only thing that can move a control and never a slot.

**One control is always on screen, and one is one hover away.** The `⋯` belongs to the whole board, so it is quiet (a flat mark) but permanent: a board that hid its only way to delete a column behind a hover would be a board you could not get out of. A card's `✕` belongs to what is *under the pointer*, so it carries `CONCEALED_CLASS` and is given `SHOWN_CLASS` by one `pointerover` handler that swaps them (`swap`, so two controls never light up for one hover) and by a `pointerleave` that takes it back. A concealed control is `opacity: 0` **and** `pointer-events: none`: a hidden `✕` that still took clicks would eat the press meant to drag the card it is hiding on, which is the one thing a card has to keep. So `.is-shown` puts `pointer-events` **back** — revealed and pressable are two separate things, and a control that is only the first is worse than none, because the press falls through to the diagram under it and nothing appears to happen. For the same reason a control is revealed by the pointer being *on it* (`onOver` resolves `event.target.closest('.mermaid-kanban-btn')` before it hit-tests the diagram): `columnAt` refuses a press on a column's own name, because that is a rename, and a control laid over that name would then be one no hover can turn on. A `✕` is hidden while `.mermaid-preview.kanban-dragging` for the same reason from the other side — a card in flight is not where it was, so its `✕` would sit in the gap it left. The `✕`s are held in a `Map` from the card element they belong to (`cardRemoves`), never in an index into `cardElements(svg)`: the board is drawn with a slot in every column, so a card's index among *all* the cards drawn is not its index among the ones that can be deleted, and a slot — which has no `✕` at all — is simply not in the map.

**The menu is a popover over a board, not a dialog on it.** One at a time (`closeMenu`), and the `⋯` that owns it is remembered (`openMenuFor`) so pressing *that* one is the toggle and pressing any other is a move — without that, a second `⋯` could only ever close the first menu. The list hangs off its own `⋯`: right-aligned to it and `MENU_GAP` under it, pushed through `place()` immediately rather than on the next resize, because the list is built long after the layer's own `place()` ran and would otherwise sit over the first column. A real column that is not the last one gets exactly `Rename column` / `Delete column` (the last one gets no delete, and the drawn column at the end gets no `⋯` at all — it is not a column yet), and the rename is wired to *the very mapper a click on the header uses*, found by position (`targets.find((entry) => section.contains(entry.el))`) rather than by name — two columns may share a name. **No item names the column.** An item belongs to the `⋯` it hangs off and that `⋯` already says which column it is, so a name in the item is a name repeated in a place a *translation* of it would have to be kept in step with the prompt's; the prompt (`promptForKanbanDelete`) is the one place that names what goes, and it still does. The corollary is that the menu is `MENU_WIDTH` wide and the *text* is bounded by it (`white-space: normal`, `overflow-wrap: anywhere`): a label wider than the menu wraps inside the popover instead of widening it off the board, which is what stops a column with a 60-character name pushing a control past the edge of its own column. Escape and a pointer off the list or the board take it away; a press anywhere that is not the list does too, and the `⋯` and the items stop the press reaching it, so the `⋯`'s own click is the toggle. **The gap is walkable, because the list stops the press itself** (`menuList` also stops `mousedown`, so a `click` can never be born out of a press the board ate): the `MENU_GAP` between the `⋯` and the list is a hole in the popover with the board visible through it, and the pointer crosses it on its way down every single time, so the list draws a `::before` bridge over it of exactly the gap's height — the one number both halves read (`--mermaid-kanban-menu-gap`, with `menuGap()`'s 6px fallback for a board with no stylesheet). A `::before` is not an element, so a hit test over the bridge reports the list; `elementFromPoint` is how the real-engine test knows the hole is closed.

**The board is drawn with somewhere to add, and the document never sees it.** A board's shape is obvious while you are looking at it and not at all once it is a paragraph of source, so the places to add are *drawn*: `kanbanAuthoringSource` (`src/mermaid-edit.ts`) appends a `slotc<n>` card to every column and a `slotn` column to the end, each carrying `KANBAN_CARD_SLOT` / `KANBAN_COLUMN_SLOT` as its label, and the node view renders **that** while the diagram is editable (`src/node/mermaid.ts`), never the document's own source. A drawn slot is therefore laid out by mermaid itself, which is the whole of why it beat the controls it replaced: an empty column's band is sized to its header alone, and a 24px bar laid over that name covered the rename target — where a card-shaped thing drawn *in* the band makes the band a card tall, gives every column a place to add without a single absolutely-positioned sibling, and cannot collide with the toolbar or a horizontal scroller, because it is not one. The reserved ids are what make this safe: `/^slot[cn]\d*$/` is an id nothing else on a board would carry, so a card the user has genuinely titled `+ Add a card` is a real card (`isKanbanCardSlot` / `isKanbanColumnSlot` are the only readers), and every commit runs the source back through `kanbanRealSource`, which strips an untouched slot and keeps a *named* one as clean content (`[Fresh]`, `col1[Archive]` — a fresh id from `freshKanbanId`, which steps over the ids already on the board, cards included) — the document is never asked to hold a slot. Everything that used to walk the board as chrome has to know the difference: `kanbanColumnCount`/`realKanbanColumns` answer "how many columns" (the menu offers no delete when it is one), `cardsIn`/`kanbanColumnCardCount` answer "how many cards" (a delete prompt must not claim it is taking slot cards), and `slotAt` is where a *new* card goes — the drawn slot's own place, so the slot stays the place the next card would go. A press on a drawn slot is a request for a title, not a drag: the pointer handler returns before `armCardDrag`/`armColumnDrag`, and the drawn column is not a column to drag either. `onSlotClick` finds the slot with `drawnElementAt` (the event's own target first, then the coordinate hit test) and then *defers to the label editor*: a click on a label is that label's business, so the column slot hands `headerTarget(band)` to `openLabelEditor` and a new column is named by the very editor its own header is renamed by. A card slot instead opens the composer at the slot's own `box()` (`slotComposerBox`), which is why an in-place assertion reads the field and the slot in *one* snapshot — the page settles between two reads, so two boxes read at two moments are two moments of the layout, not two boxes. **A drawn slot's label is a placeholder, so the field that writes over it is empty.** A card slot is not even a label target at all (the card filter in `attachMermaidEditing` drops it, and its composer opens from the slot), but a column's *is* one — its name is a label like any other, which is the whole reason the slot can be named by the editor that renames it — so the *same* press on a slot's text and on the band around it must not open two different fields. Both therefore pass one `FreshField` (`columnField(band)`: empty value, `placeholder: 'Column name'`, `tone: 'new'`, the band's width at `COMPOSER_HEIGHT`) into `openLabelEditor`, and the generic click handler works it out from the *same* slot walk (`slotBand` is `sectionElements(svg)[slots.column]`, not a CSS class, so a class that outlived its render cannot make a real header open empty). What is being filled is a column, so the field stands in the band and not over the text on it, and `RENAME_FIELD_WIDTH`'s floor is dropped: a band is already wider than a name. An empty commit is refused by the `usableKanbanLabel` guard every label already had, with the same reason a card gives — a `kanban` header with nothing in it is not a column.

The layer is positioned the way the drag indicator is *not*: these are absolutely-positioned HTML siblings of the svg, from `container`-relative rects through one `place()`, and what `place` reads is *re-read on every event that can have moved it*: a `ResizeObserver` on the svg, on the preview **and** on the editor scroller, plus their `scroll` events. The svg alone is not enough (a window resize narrows the preview while the svg keeps the size mermaid drew it at, so the observer never fires), the preview alone is not enough (a composer hanging below a short board scrolls the *editor*), and no observer covers the rest: the board is *centred* in the preview, so the svg slides inside it when the block around it grows, moving every control without changing the size of anything measured. So an event asks `schedule()` rather than placing directly, and a `place()` that moved something asks for another — a self-limiting settle loop that ends as soon as a place moves nothing, which is what makes a re-placement a convergence rather than a per-frame cost. Every re-render *rebuilds* the layer, so the controls exist only in edit mode and are gone after Done. A card's `✕` is smaller (`REMOVE_BUTTON_HALF * 2` against `KANBAN_BUTTON_HALF * 2`) and sits in the card's own top-right corner, `KANBAN_BUTTON_EDGE` in from both edges, so it covers as little of the title as a pressable target can. It is offered only where the walk is trustworthy: `cardElements(svg)` must match the parsed model's card count, and the columns must match the sections', or the layer is skipped rather than offering to delete something it cannot name. The drawn slots are none of this — they are drawn by mermaid, laid out by mermaid, and repositioned by mermaid.

**A composer is taller than the slot it fills, so the block grows for it.** A field is absolutely positioned, so it contributes nothing to the block's height — and an empty column's band is only a header and a card tall, so a field asking for a long card title hangs below the band, and at the end of a document the part that hangs is not something the editor can scroll to: the dialog is simply cut off. So `openInlineInput` measures the difference and sets the block's `padding-bottom` to it (`FIELD_MARGIN`), scrolls the field into view only when it really grew, and puts the padding back on close. It also takes the rect as a *function* when the caller has one (`spec.rect: DOMRect | (() => DOMRect)`, reported through `onPlaced`) and is repositioned from the chrome's `place()` like every other control, because a composer stands where the control it replaced stood and the board moves under it; the chrome drops the entry as soon as the field is gone, which is the only signal that it closed. A column's name is one line and it is edited by the label editor, not by a composer, so `COMPOSER_HEIGHT` only ever sizes the *card* composer — which is the one that grows with the title, and the one that can be taller than the band it fills.

**A composer writes a title, so it grows with it.** `InlineInputSpec.multiline` makes `openInlineInput` build a `textarea` and size it to its own content on every `input` (`scrollHeight`, from `auto` up), capped at `COMPOSER_MAX_HEIGHT` and scrolling past it: a card title is longer than the card-shaped slot it was opened from more often than not, so a fixed box either scrolls the rest of the title out of sight or covers the columns behind it with a field nothing is being typed into. **Enter is the commit key and Shift+Enter is refused, not committed** — Shift+Enter is the way a textarea normally starts a new line and a mermaid card title cannot hold one; committing would drop the break *and* leave the rest of what was typed behind in a field that has gone, so the field stays open with the value the user has.

**A ✕ asks first, and says what it is taking.** Deleting a card or a column runs `promptForKanbanDelete(subject, consequence)` in `src/urlDialog.ts` — `Cancel`/`Delete`, with Delete in `toolbar-danger`, a note naming what goes and (for a column with cards) how many go with it, Escape and a backdrop click as cancel. It is a dialog rather than a `window.confirm` because a board is the user's document and a delete is undoable: the note says so. `removeKanbanCard` / `removeKanbanColumn` in `src/mermaid-edit.ts` are the pure patchers that answer it — the first removes one card line, the second the column header and every card indented under it, and the second **refuses on a board of one**, because emptying the last column leaves a `kanban` with no columns, which is not a board. Nothing is patched until the answer is `true`, and each is one `setNodeMarkup`, so one undo takes the whole deletion back. The walk that builds a column's header controls is positional (`doc.columns`, `cardElements(svg)` filtered by which band a card's centre is in), which is the same mapping the drag already used, and a card that lands in no band gets no ✕ rather than a guess at which column it is in.

**A field that adds something must not look like one that overwrites something.** `openInlineInput` builds a `div.mermaid-edit-field` around the input rather than the bare input it used to be, because the bare one had no way to carry a shape: a rename gets no `tone` and a `minWidth` of `RENAME_FIELD_WIDTH`, while an add gets `tone: 'new'`, which is what the dashed accent edges in CSS are for, plus a `minWidth` wide enough for a real card title (`NEW_FIELD_WIDTH`). It needs **no words**: it used to print a caption above the field (`New card in <column>`, `New column after <column>`) and that was one thing too many — the place the field was opened from is *drawn in the board*, so the board is the sentence the caption finished, and `tone: 'new'` says "this creates" without a label to keep in step with the source, truncate, or translate. The wrapper owns the geometry and the input is its only child, so the field is one box to place, size and clip to nothing (an absolutely positioned child of a horizontal scroller is placed from the scrolled content, not from the visible box, so the preview's own scroll has to be added back), and `field.remove()` on commit/cancel takes the whole thing with it. The `onAccept` contract is unchanged and still the only place a title can be refused: `true`, `false`, or a *reason* (`usableKanbanLabel`), so a name mermaid cannot read is refused before it is committed, by the same rule the label editor has always used.

**A new board is `insertKanban` end to end.** `buildKanbanSource(columns)` (pure, in `src/mermaid-edit.ts`) turns names into a runnable diagram — `['Todo','Doing']` -> `kanban\n  col1[Todo]\n  col2[Doing]`, with unwritable names dropped, repeats suffixed ` (2)`, and `''` when nothing survives. `promptForKanbanColumns()` in `src/urlDialog.ts` asks for the names, one per line: a textarea, so plain Enter is a *newline* and Ctrl/Cmd+Enter (or Add) confirms. `insertKanbanSource()` in `src/node/mermaid.ts` does the insert as **one** transaction with the mode already set (`openDiagramEditIn()`, shared with `enterDiagramEditMode`), so one undo takes the whole board away; `insertKanbanBoard()` wraps the dialog, the builder and the "none of those names can be used" error, and is what the Insert-menu QAction (`insertKanban` in `MenuCommands`, and the toolbar's Kanban button) calls.

**A kanban title is free text, quoted on the way in.** Mermaid's kanban grammar reuses the flowchart *shape* delimiters inside a `[…]`, and a *quoted* label can hold them — mermaid draws it as the text inside the quotes and nothing else. So `kanbanInnerLabel()` is the single writer used by all three paths — a new card, a new column, a rename — quoting anything in `KANBAN_QUOTE_CHARS` (`[ ] ( ) { } @ >`): `Fix (the bug)` is `["Fix (the bug)"]` in the source and `Fix (the bug)` on the board and in the label editor, and the quotes are never anything the user typed or saw. That set is the whole shape syntax, deliberately a **superset** of what real mermaid rejects bare (a 40-diagram sweep says only `]`, `(`, `)`, `}` — `[`, `{`, `<` and `>` all render), because the two extras are ours: an unquoted label holding `@{ … }` is silently eaten as metadata, and one holding `>` renders but `kanbanLabelSpan` refuses it as a shape with no closer — a title the user typed that is not the title the board shows. Do not narrow it. The reader mirrors the writer: `kanbanLabelSpan()` recognises the quoted form *first* (before the shape search, or a bare `"Fix (bug)"` finds its own `(` and maps to `bug`) and returns the **whole quoted run, quotes included**, while `parseKanban` unquotes it into `label` — so a rename replaces the run and a label already written with quotes keeps them (`kanbanQuotedLabel`; `replaceSpans` writes one spelling over every span, so a mixed board takes the conservative one). What quoting cannot carry is refused, not committed: `UNUSABLE_KANBAN_LABEL` is a `"` or a line break, checked by `usableKanbanLabel()` at the *UI* boundary (the card slot composer's, the menu's `onAccept`, and `openLabelEditor`), which returns `kanbanLabelRefusal()` — `openInlineInput`'s `onAccept` returns `true`, `false`, or a *reason*, and a reason flashes the input red and shows a notice. A committed title mermaid cannot read would leave the board on its last good render with the card the user just typed visible nowhere, which is the whole failure this quoting exists to prevent. The one shape the mapper must still refuse blind is an *unterminated* quote (`["Half open`): nothing says where the label ends, so `label` is `null` and the label is not offered.


The real-engine tests live at the end of `tests/test_window.py` and the shared WebEngine helpers in `tests/mermaid_render.py` (not `test_*.py`, so pytest does not collect it). They render in that module's already-open session window on purpose: a `MainWindow` is a WebEngine page, and the dark-probe plus template sweep already take two, so a module of its own (or a fourth window) turns the suite red for no reason. `QTest` mouse injection never reaches the page, so those tests dispatch JS-synthesised `PointerEvent`s.

## Testing quirks

- Qt must run offscreen headlessly: `QT_QPA_PLATFORM=offscreen` + `QTWEBENGINE_DISABLE_SANDBOX=1`. `tests/conftest.py` sets these via `os.environ.setdefault` *before* importing PySide6 — never import PySide6 before the env is set.
- QtWebEngine `runJavaScript` does **not** await Promises. The packaged-binary smoke test (`EDI_SELFTEST=1`, offscreen) probes sync JS snapshots (`window.__selftest`) and, once the page finishes loading, prints one `SELFTEST {...}` line and exits 0. The app boots a **home screen** (`#app[data-view='home']`) instead of a welcome tab, so the smoke loads the page with `?selftest=1` (backend sets the query when `EDI_SELFTEST=1`); `src/main.ts` checks that flag and opens the Welcome doc so `__selftest.title` still reads `Untitled — Edi`. A 25s watchdog prints `SELFTEST_TIMEOUT` and exits 1. It uses `os._exit` to skip Qt teardown (a wedged renderer can otherwise hang the process and swallow output) and must not depend on async values or the bridge being ready. When `EDI_SELFTEST_OUT` names a file, the same verdict line is also written there before exit — required for the windowed Windows build, which has no attached console (`console=False` makes Python's sys.stdout None); both the Wine build (`scripts/build-windows-wine.sh`, bash) and the desktop `scripts/build-windows.ps1` parse that file instead of stdout. `_run_selftest` first writes a `SELFTEST_BOOTING` heartbeat to that file so a hung smoke can distinguish "still self-extracting / Qt still starting" (no heartbeat) from "Python booted but QtWebEngine never loaded" (stuck on BOOTING). `build-windows-wine.sh` polls the file rather than using a fixed wait — succeeding the moment a `SELFTEST {...}` verdict appears, but under Wine the smoke is fundamentally structural: it stops early (and classifies `SELFTEST_SKIPPED_ENVIRONMENTAL`) the moment the proven Chromium-init crash markers land in the boot log instead of grinding the **20 min budget** (`EDI_SMOKE_BUDGET_MIN` overrides), and hard-fails only on extraction/DLL-load/anomaly evidence. `build-windows.ps1` does the same on a real Windows desktop with a **3 min budget** (same `EDI_SMOKE_BUDGET_MIN` override). Run 2 hung; runs 3+ exit with code `-1`, which is the windowed bootloader relaying the **child Python process's** nonzero exit — NOT a bootloader/corrupt-archive abort, and `%TEMP%\_MEI*` was a complete extraction all along (the old "partial extract: 62 files" DIAG counted only top-level entries). When the console twin shows Python booting, the actual packaged-binary failure mode is a DLL load error (e.g. `ImportError: DLL load failed while importing QtWebEngineCore: The specified module could not be found.`). Cause (proven on GitLab's former `saas-windows-medium-amd64` runner, since replaced by the Wine build): all 20 Qt6 DLLs — every WebEngineCore companion AND Qt6WebEngineCore.dll itself — are present in the bundle; the load still fails because **Qt6WebEngineCore.dll has hard static imports of `dcomp.dll` (DWM compositor) and `bthprops.cpl` (Bluetooth shell) that Server-SKU runners do not have** (proven by parsing the win_amd64 wheel's import table with `pefile`, and by PyInstaller warning on exactly those two — everything else, incl. `msvcp140.dll`, resolves from System32). Linux pulls only the Qt libs via ELF `DT_NEEDED` so it works; and `dcomp.dll`/`bthprops.cpl` exist on normal Windows 10/11 desktops. That was necessary but NOT sufficient: the exes built by that runner (and by early Wine builds here) also shipped with **zero Qt plugins** because **Wine lacks System32's `icuuc.dll`/`icuin.dll`**, which `Qt6Core.dll` hard-imports (20 `ucnv_*` symbols, proven via `pefile` and a wine loader trace `err:module:import_dll Library icuuc.dll ... not found`). PyInstaller 6.22's Qt hooks discover the Qt install by importing `PySide6.QtCore` in an isolated subprocess; with ICU unresolvable that probe failed, the hooks found no plugins, and the onefile booted with "no Qt platform plugin could be initialized" on any real desktop. Nobody ships the DLL: the win_amd64 wheels carry only `resources/icudtl.dat`, official Qt 6.11.1 bin has no ICU DLL, and `icuuc.dll` is a Windows system DLL (present in every real System32 ≥ 1703; Wine bundles it only since the **11.5 development line** — so `Dockerfile.wine` installs **winehq-staging**, never wine-stable 11.0). The fix (2026-09): the build copies Wine's bundled ICU (`/opt/wine-*/lib/wine/x86_64-windows/icu*.dll`) into the prefix's `site-packages/PySide6/` so the hook probe succeeds and the plugins get collected canonically; `edi.spec`'s win32 branch then force-appends those ICU DLLs to the bundle (deduped, like the WebEngine companions) so the exe is self-contained even on no-ICU Windows. Both `build-windows-wine.sh` and `build-windows.ps1` therefore probe/make the venv's QtWebEngineCore import work **before** the frozen smoke (probe fail ⇒ `SELFTEST_SKIPPED_ENVIRONMENTAL`, exit 0, packaging proceeds; the `.ps1` desktop path stages System32's ICU into the venv the same way and still runs the FULL render smoke on real Windows). Under Wine specifically, the frozen onefile boots — extraction + Python + Qt init are proven — but QtWebEngine's Chromium then FATALs during init (`network_change_notifier_win.cc`: `WSALookupServiceBegin failed with: 8`; `hwnd_util.cc:65]: 1400`) and Wine parks an invisible `winedbg` dialog, so the script bounds the smoke, stops early when those markers land, kills the process tree, and classifies the crash `SELFTEST_SKIPPED_ENVIRONMENTAL` — while still hard-failing on extraction errors / `DLL load failed` / missing plugins (the CArchive structural check, 4a, is the load-bearing regression gate for the pluginless-bundle bug). The probe must run under `$ErrorActionPreference='Continue'` with `2>&1` capture and then restore EAP — Windows PowerShell 5.1 promotes native-command stderr to a terminating `NativeCommandError` when EAP is 'Stop' (that aborted the job before the skip logic ran on the first attempt). `edi.spec`'s win32 branch still explicitly appends the WebEngine companion set (`Qt6WebEngineCore/Qt6WebEngineWidgets/Qt6Qml/Qt6Quick/Qt6QuickWidgets/Qt6QmlModels/Qt6QmlWorkerscript/Qt6Positioning/Qt6WebChannel/Qt6Network/Qt6PrintSupport`) to `a.binaries` as `(dest, src, 'BINARY')`, deduped against `b[0]` dests already collected. Note the bundle root holds NO Qt DLLs — they extract to the `PySide6/` subdirectory (System + python DLLs sit at the root; the msvcp140 family is never collected because PyInstaller excludes everything resolved under `C:\Windows`, which is fine — System32's copy loads). `run_edi.py` dumps the bundle inventory and, on import failure, a **PE import-table lint** of the failing Qt module (`[selftest] OK <name> -> bundle|System32` / `MISSING <name>`) under `EDI_SELFTEST`. The windowed bootloader (`runw.exe`, `console=False`) swallows the fatal message into an invisible dialog; `edi.spec` therefore also builds a **console twin `Edi-selftest.exe`** (win32 branch only, shares Analysis/pyz, ~+30s pack) that `build-windows.ps1` smoke-tests instead: `Start-Process -RedirectStandardOutput/-RedirectStandardError` captures the real `Error extracting <entry>: <errno>` line and dumps it into the job log (still also parses `EDI_SELFTEST_OUT`). The twin is deleted before the artifact phase so the `dist-app/Edi-*.exe` glob ships the versioned onefile **and** the installer (`Edi-<v>-win64-setup.exe`) — the NSIS installer is now ALSO built by the wine job (native Linux makensis, `nsis` baked into the image; no Wine needed). The Path-quirks lesson from the old runner still applies: makensis resolves relative `File`/`OutFile` paths against the **script's** directory, not the CWD, so `build-windows-wine.sh` passes `-DSETUPEXE`/`-DICO`/`-DOUTEXE` as **absolute** paths (Linux makensis also takes `-D`, not `/D`); `edi.nsi` exposes an optional `OUTEXE` define so the output lands in the checkout root, not `packaging/`. `build-windows.ps1` can still build one on a real Windows desktop (`packaging/edi.nsi` stays desktop-compatible).
- `pyproject.toml` sets `pythonpath=["."]`, so run pytest from the repo root; running it elsewhere breaks `import backend`.
- QtWebEngine segfaults at interpreter exit in headless/container pytest runs (tests pass, job fails with exit 139). `tests/conftest.py` `pytest_sessionfinish` registers an `atexit` `os._exit` that passes pytest's real exit status and skips Qt teardown. Keep the handler registered only at session end, not at import, so real crashes mid-run still propagate as signals.
- The onefile binary self-extracts ~450 MB to `$TMPDIR` on every launch. `/tmp` is often a small tmpfs, so the smoke tests (`build-pyzip.sh`, CI `build` job) point `TMPDIR` at a disk-backed `build/tmp`. A full write there surfaces as `Failed to extract ...: decompression resulted in return code -1` — that return code is the bootloader's `Z_ERRNO`, set only when `fwrite` fails while unpacking (a corrupt archive would show -2/-3/-4), so it means temp space ran out, not a broken binary. The selftest `os._exit`s without Qt teardown, so a QtWebEngine subprocess can outlive the parent and re-launch the onefile bootloader; `build-pyzip.sh` therefore waits for `dist-app/edi` processes to exit before removing the smoke temp dir, or a late one fails with `Could not create temporary directory!`.

## Distribution (hard-won constraints — do not break)

- The shipped binary MUST be built on **Ubuntu 22.04 (glibc 2.35)** so it runs on older desktop Linux. `scripts/build-pyzip.sh` pins everything inside Docker for this; host-built binaries are not portable and must not be shipped.
- **`libstdc++.so.6` and `libgbm.so.1` must never be bundled** (`edi.spec` `GL_HOST_DEPS` filters them out). Bundling the 22.04 copies breaks host Mesa/LLVM loading: libstdc++ crashes with `GLIBCXX_3.4.32 not found`, and libgbm (Mesa's buffer manager) makes QtWebEngine's GPU process print `did not find extension DRI_Mesa version 1` / `EGL: Failed to initialize GBM device` and fall back to software rendering on any host whose Mesa is newer than 22.04's.
- **Qt bundle pruning in `edi.spec`**: Edi uses only the QtWebEngine *widgets* API, so `excludes=['PySide6.QtQml', 'PySide6.QtQuick']` keeps hook-PySide6.QtQml from firing — otherwise it drags in the entire `qml/` tree (~4,850 plugin files) plus every Qt lib those plugins reference (Qt3D, QtQuick3D, QtCharts, QtGraphs, QtVirtualKeyboard, ...). The libQt6Qml/libQt6Quick shared libs WebEngineCore genuinely links against are still pulled by binary dependency analysis, so this is safe. `QT_DEAD_PREFIXES` additionally drops the on-screen-virtual-keyboard input-context plugin and its libs (match the soname-form dest too — PyInstaller emits both `PySide6/Qt/lib/...` and top-level `libQt6...` entries). Verify with `rg -c 'libQt6' build/edi/PKG-00.toc` (expect ~100, not 468) and the smoke test.
- **PyInstaller archive compression**: the CArchive (PKG) step defaults to zlib **level 9**, which makes the onefile pack step dominate build time. Build with `PYINSTALLER_ZLIB_COMPRESSION_LEVEL=1` (set in `Dockerfile.pyzip` and the CI `build-linux` job) — ~3x faster pack; the binary grows ~18 MiB but every release wrapper (.deb/.rpm/.tar.gz/.AppImage) recompresses anyway.
- **Frontend must be a single JS bundle — no runtime `import()`**: the app ships to QtWebEngine as `dist/index.html` under `file://`, and QtWebEngine intermittently fails runtime dynamic module fetches under load (`Uncaught (in promise) TypeError: Failed to fetch dynamically imported module`). That was the root cause of the chronically flaky `tests/test_mermaid_templates.py` (mermaid's internal `mermaid.core.js` split chunk failing) and can hit real users as "Mermaid render error". `vite.config.ts` therefore sets `build.rolldownOptions.output.codeSplitting: false` — one ~5.4 MB minified bundle, no async chunks (the remaining `import(` in the minified output is ESLint-mode regex text / an `import.meta.resolve` feature-detect). Do NOT re-enable code-splitting for "perf" — the depot is local disk; the lazy-loading it buys has cost intermittent renderer errors.
- The app icon (`scripts/assets/app-icon.png`) is generated from `scripts/generate-icon.mjs` and bundled via `edi.spec` `datas`. `backend/window.py` `load_app_icon()` guards `sys._MEIPASS` (built binary vs. source run) — keep that guard. The about dialog reuses the same artwork (`load_about_logo()` scales `scripts/assets/app-icon.png`); the old `assets/edi-logo.png` was deleted — do not reintroduce a separate logo. The same script now also writes `app-icon.ico` (16–256, for the Windows EXE resource/installer) and `app-icon.icns` (16–1024, for the macOS BUNDLE); both are gitignored build artifacts regenerated before each native pyinstaller run.
- **Windows/macOS binaries**: PyInstaller cannot cross-compile, so each OS's bundle is produced on a machine that provides that OS's runtime. Windows is now built on Linux via a WineHQ container (see the Wine build bullet); macOS still MUST build on macOS. `edi.spec` branches on `sys.platform` over a shared `Analysis` (datas + QtQml/QtQuick excludes are platform-independent): only the Linux branch applies `GL_HOST_DEPS` / `QT_DEAD_PREFIXES` and keeps the lowercase `edi` EXE name; the `win32` branch names the EXE `Edi`, attaches `scripts/assets/app-icon.ico` and a `VSVersionInfo` (version parsed from `backend/__init__.py` at spec time so it cannot drift from the tag); the `darwin` branch makes `Edi` + a `BUNDLE` into `Edi.app` with an Info.plist declaring the icon and `bundle_identifier=com.mrdanpsmith.edi`.
- **Windows CI**: the `build-windows` job builds the `.exe` on ordinary Linux runners inside the `ghcr.io/<owner>/edi-wine-builder:jammy` image (built+pushed by `images.yml` from `Dockerfile.wine`, on tag-run/manual-validation v* runs, alongside the Linux `build-linux` job). `Dockerfile.wine` is Ubuntu 22.04 + WineHQ **`winehq-staging`** (i386 arch enabled; staging tracks the ≥11.5 devline whose Wine bundles the system ICU that `Qt6Core.dll` needs — wine-stable 11.0 is too old) with the **win_amd64 wheels baked in** (`/opt/wheels`, downloaded at image-build time — no Wine TLS) and the**Windows Python installer** (`/opt/py`, pin 3.12.8, shared via `requirements-win.txt` = `PySide6==6.11.1` + `pyinstaller==6.22.0` + `pefile` + `pywin32-ctypes` + `defusedxml`, `REQ_HASH` build-arg invalidates the wheel bake when the pins change; `EDI_WINE_REFRESH` does the same for the unpinned winehq apt layer). pefile/pywin32-ctypes are PyInstaller's `sys_platform == "win32"` deps; `pip download --platform win_amd64` on Linux evaluates markers against the *host*, so they must be pinned explicitly or the offline install fails. No prefix is baked: `scripts/build-windows-wine.sh` creates `build/wine-prefix` at job time (pin-stamped; reruns reuse it). The Python installer is a **GUI bootstrapper** and is killed instantly headless (wine reports 128+SIGINT), so prefix init + the installer run under `xvfb-run`; pip/PyInstaller are console apps and stay headless. CI container jobs run as root and **Wine refuses to run as root**, so the script re-execs itself as an unprivileged `ediwin` user (chowning just `build/` + `dist-app/`). The same script is the **local** iteration path: it `docker run`s the image with the checkout mounted at `/builds/edi` as the host uid. The frontend `dist/` + `app-icon.ico` come byte-identical from the `frontend` job's artifacts, so the job needs no Node/npm. Validation is STRUCTURAL (see the smoke bullet) — a full render only happens by running `scripts/build-windows.ps1` on a real Windows desktop (it remains the desktop path: `.venv-win` for `PySide6==6.11.1`/`pyinstaller==6.22.0`, offscreen smoke via `EDI_SELFTEST_OUT`, renamed to `Edi-<ver>-win64.exe`). The NSIS installer (`Edi-<v>-win64-setup.exe`) is now built by the same wine job (native Linux makensis; see the smoke/ICU bullet for the path-quirk rules). The `release` job pulls the `.exe` through its `needs` edge (explicit `needs` — build-windows — limits artifact downloads to exactly what each job consumes).
- **macOS CI runs on GitHub Actions' free arm64 `macos-15` runners** (the `build-macos` job, gated to `v*` tags / manual validation like the other binary jobs). `scripts/build-macos.sh` (Darwin-only; brew-installs Node 20+/Python 3.10+ as needed) mirrors the Linux steps into `dist-app/Edi.app`, ad-hoc code-signs it (`codesign --force --deep -s -`, arm64 will not launch unsigned), smoke-tests the bundle binary, then wraps it into `dist-app/Edi-<ver>-macos-arm64.dmg` (drag-to-Applications, `Applications` symlink). Apple Silicon only; unsigned/not-notarized (no Apple Developer account), so Gatekeeper warns on first open — accepted, documented tradeoff; don't add signing stubs that imply Developer-ID signing works.
- `PySide6==6.11.1` and other pins live in `requirements.txt`; the Windows build mirrors them (`PySide6==6.11.1` + `pyinstaller==6.22.0` + `defusedxml` in `requirements-win.txt`, consumed by Dockerfile.wine and `scripts/build-windows.ps1`); keep PySide6 pinned (Qt releases break the WebEngine hooks).
- `backend/tables.py` (Insert → Spreadsheet) parses ODS/XLSX XML with **`defusedxml`** as a drop-in for `xml.etree.ElementTree` — plain ElementTree is XML-bomb vulnerable on user-opened files, and bandit greets it with a Medium finding. It is a runtime import, so every PyInstaller build venv must install it, not just the dev/CI venv: `Dockerfile.pyzip`, `Dockerfile.wine`, `scripts/build-windows.ps1` and `scripts/build-macos.sh` each pin it explicitly alongside PySide6 (PyInstaller collects it automatically once it's importable).

## CI (GitHub Actions — `.github/workflows/ci.yml` + `release.yml` + `images.yml`)

- Two workflows, two pipelines: **`ci.yml` (name `CI`)** is the normal commit pipeline — runs on every `pull_request` and on every push to `main` / `release/**` branches, and only runs the testing phases (`frontend` + `test`), never binaries or releases. **`release.yml` (name `Release`)** is the full tag-gated DAG (`v*` tags or manual `workflow_dispatch`, `VER` defaulting to `0.0.0`) — the same quality gate plus the platform builds, packaging, and publishing. The `frontend`/`test` job bodies are **deliberately mirrored** across both files (each pipeline stays self-contained); that's why `.jscpd.json` ignores `**/.github/workflows/**`. The single `concurrency: ci-${{ github.ref }}` covers both events on purpose: a PR's `github.ref` is `refs/pull/N/merge`, so a new push cancels the superseded run without ever colliding with the `refs/heads/main` group, and a merge still runs the push job.

- Coverage stays **cobertura** — that is now load-bearing, not incidental: GitHub's **built-in** coverage dashboard (public preview since 2026-05, explicitly the Codecov/Coveralls replacement) ingests Cobertura only, so the two reporters must keep emitting it and the two paths must keep their names. `npm run coverage` → `coverage/cobertura-coverage.xml` (Vitest v8), pytest → `coverage-py/cobertura-coverage.xml` (pytest-cov 7 has no `cobertura` reporter; `xml:...` output is Cobertura). The frontend denominator is **every `src/**` file**: Vitest 4 removed `coverage.all`, and the v8 provider globs `coverage.include` after a full run and reports what it never loaded, so a module no test imports lands at 0% (verified with a throwaway `src/zzNeverImportedProbe.ts`: 63 → 64 classes, row at 0%). Do not "fix" that by adding `all: true` — the key is gone and the setting is silently inert. Two consequences of the same path: a single-file re-run skips it (`cleanOnRerun`), so `npm run coverage` is the report that counts, and `src/test-setup.ts` is missing by accident rather than by rule (the runner loads it uninstrumented, so it is in neither bucket — and `coverage.exclude` must stay unset, since replacing the default list would pull all 53 `*.test.ts` files into the report).
- The `test` job uploads both to that dashboard with `actions/upload-code-coverage@v1` — one step per language (`TypeScript` / `code-coverage/vitest`, `Python` / `code-coverage/pytest`) — and they render together as one PR summary from `github-code-quality[bot]`, with uncovered changed lines annotated on the Files-changed tab. No third-party service, no upload token: it needs only the job-level `permissions: code-quality: write` (added alongside `contents: read`, since a job-level block *replaces* the workflow default). Two deliberate choices keep reporting out of the gate: `fail-on-error: 'false'` (the API is preview, so a 5xx / rejected payload / processing timeout must not redden a green run) and an `if:` limited to `pull_request` or the default branch — the action's eligibility step shells out to `gh pr list` for a push to *any other* branch, and `edi-builder:jammy` ships no `gh`, which hard-fails the step. Fork PRs are skipped by the action itself (its own `COVERAGE_PR_HEAD_REPOSITORY` check), so no `if:` fork guard is needed. The `Publish coverage summary` job-summary step stays as the per-run text twin of the dashboard. **PR-time coverage rides on the `pull_request` trigger `ci.yml` gained** (release.yml stays tag-gated, so a tag run's upload is skipped by the `if:` above): the action then resolves the context itself and uploads against the **PR head SHA**, which is what makes the Files-changed annotations land on the right lines. Note the trigger also means every branch push now runs the whole gate — with `cancel-in-progress: true` keyed on `refs/pull/N/merge`, a superseded run is killed rather than billed.
- QtWebEngine hangs in containers with small `/dev/shm` / no GPU: set `QTWEBENGINE_CHROMIUM_FLAGS="--disable-dev-shm-usage --disable-gpu"` (and `QTWEBENGINE_DISABLE_SANDBOX=1`) for any headless Qt run — the workflows set these globally.
- `test` needs `dist/` for pytest (backend tests load `dist/index.html`); the `frontend` job builds it and `test` downloads the artifact.
- Compute-conscious CI setup: most jobs run **inside** a prebuilt **builder image** (`ghcr.io/<owner>/edi-builder:jammy`, built from `Dockerfile.ci` by `images.yml` — on main when `Dockerfile.ci`/`requirements.txt`/`.github/workflows/images.yml` change, never on tags, and manually via `workflow_dispatch`; run it once manually after a fresh import so ghcr has the images). It bakes the ~30 Qt runtime libs, Node 22, and a venv at `/opt/edi/venv` (PySide6==6.11.1, pyinstaller==6.22.0, pytest, pytest-qt, pytest-cov, defusedxml, bandit, pip-audit). Jobs use it as a `container:` and link the venv with `ln -s /opt/edi/venv .venv` (package-linux.sh hardcodes `$ROOT/.venv`) and `npm ci` where needed. The **`build-windows`** job instead runs in a second pushed image (`ghcr.io/<owner>/edi-wine-builder:jammy` from `Dockerfile.wine`), so its ~1 GB Wine+wheel payload never pollutes the everyday pull. Both are pushed by `images.yml` (triggered on `Dockerfile.wine`/`requirements-win.txt` changes too). **Never pip-install into the baked venvs at job time** — they're read-only image layers; bake changes into the images. `images.yml` must use a `docker-container` buildx driver (the default `docker` driver errors with "Cache export is not supported for the docker driver" on `--cache-to type=registry`) and must pass `-f Dockerfile.ci` explicitly — the repo root also has a plain `Dockerfile` (the app's container image: node frontend stage + `ubuntu:26.04` runtime), which buildx builds by default and would produce a node-less image with the venv at `/app/.venv` instead of `/opt/edi/venv`. Jobs pull the ghcr images as **public packages**, so no auth and no fork-registry failure.
- npm caching: `actions/setup-node` `cache: npm` (frontend + macOS jobs) — never `node_modules/` or `.venv/` (they exceed GitHub's cache cap and caused misses; `npm ci` deletes node_modules anyway). The Linux/Windows binary jobs need no Node at all: they consume the `edi-web` artifacts (macOS is the exception — `build-macos.sh` does its own `npm ci`).
- The quality gate is split over two jobs in both pipelines: `frontend` runs lint + typecheck + dupcheck + the production build (producing `dist/` + `.ico/.icns`); `test` runs vitest coverage + bandit + pytest + the two coverage uploads, then the network audits (`npm run audit`, `.venv/bin/pip-audit -r requirements.txt`) last so a transient network failure doesn't burn the deterministic gate. Keep local `npm run check` as the full gate.
- Binary jobs are gated to `v*` tags (or manual `workflow_dispatch`, where `VER` falls back to `0.0.0` for validation): `build-linux` runs in the jammy container (the glibc 2.35 pin), `build-windows` in the wine container, `build-macos` natively on a free arm64 `macos-15` runner. The tradeoff stands: a pyinstaller/Wine/Mac regression surfaces only on a tag or a manual run.
- Release-pipeline DAG (`.github/workflows/release.yml`): `frontend` → `test` (dist artifact); `frontend` → `build-linux` + `build-windows` in parallel (both consume the same `edi-web` artifacts, byte-identical to what `build-macos` builds itself — the platform builds never recompile the frontend, and the Windows build needs no Node) → `package` (`needs: build-linux`) → `release` (`needs: [package, build-windows, build-macos]`). Artifact downloads are scoped by name to exactly what each job consumes (`build-windows` pulls only the small `edi-web` artifacts + the wine image, never the ~193 MB onefile; `release` pulls only the four packaged files + the .exe + the .dmg).
- `release` publishes via `gh release create <tag> file...` on `v*` tags, authenticated by the runner's built-in `GITHUB_TOKEN` (job `permissions: contents: write`). It refuses to run if `$GITHUB_REF_NAME != v$(version.sh current)`. **Do not glob `dist-app/...` in the release job**: `upload-artifact` v4 flattens wildcard uploads (paths are preserved only "after the first wildcard"; multi-path wildcard uploads root at their LCA), so artifacts unzip flat at the artifact root — the win/mac files even lose their `Edi-` prefix. The job downloads all three artifacts into `artifacts/` and `find`-enumerates them (fails loudly if none landed).
- Linux dock/taskbar icon comes from a `.desktop` file (not the window icon), so the bare binary shows a generic gear without one. `scripts/install-desktop.sh` installs `~/.local/share/icons/hicolor/512x512/apps/edi.png` + `~/.local/share/applications/edi.desktop` (template `scripts/assets/edi.desktop`, `Exec` substituted); `app.setDesktopFileName("edi")` in `backend/main.py` hints the WM to match it.
- Release artifacts are versioned and wrapped: the CI `package` job (v* tags only) runs `scripts/package-linux.sh`, which wraps the already-built onefile (never recompiles; inherits the glibc 2.35 build) into `edi_<v>_amd64.deb`, `edi-<v>-1.x86_64.rpm`, `edi-<v>-linux-x86_64.tar.gz`, `Edi-<v>-x86_64.AppImage`. The `release` job publishes everything via `gh release create <tag> file...` (multi-file is supported) and refuses to run if `$GITHUB_REF_NAME != v$(version.sh current)`. `rpm` and `file` (required by appimagetool and rpm's brp scripts) are baked into the builder image.
- Runtime dependency lists live in `scripts/package-linux.sh`: `DEB_DEPENDS` (Debian names) and `RPM_REQUIRES` (different names — e.g. `libnss3`→`nss`, `libasound2`→`alsa-lib`, `libpulse0`→`pulseaudio-libs`, `libgssapi-krb5-2` merges into `krb5-libs`). The .deb is validated on a clean `ubuntu:22.04` container (apt resolves Depends and `EDI_SELFTEST=1` runs); the .rpm needs a Fedora/Rocky box for the full dnf resolution test (this sandbox cannot reach `mirrors.fedoraproject.org`). `%global _debug_package 0` in `packaging/edi.spec.in` stops rpmbuild's find-debuginfo from choking on the prebuilt binary; `rpmbuild` needs `--define "_dbpath <dir>"` when building as non-root.
- `dpkg-deb` output is forced to `-Zxz` (`packaging/control.in`) so old apt can read it; the hicolor icon set (16–512) is scaled from the 1024 source with a PySide6 `QImage` snippet (headless, no QApplication needed). AppImage uses `appimagetool` pinned to `1.9.1` (fallback: `continuous`), run with `APPIMAGE_EXTRACT_AND_RUN=1` (no FUSE in CI) from the stage dir so the output lands there. The AppImage's squashfs zstd level is lowered to 1 via `--mksquashfs-opt -Xcompression-level 1` — mksquashfs's default level 15 is slow on the ~180 MB payload for a few percent less size.
